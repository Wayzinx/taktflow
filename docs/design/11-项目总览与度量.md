# 11 · 项目总览与度量

## 解决什么问题

管理者和协作者要一眼看到：有哪些需求、各自到了哪个阶段、卡在哪、谁在等谁、花了多少、质量怎么样。

## 页面

**项目总览**
- 需求列表：每行一个阶段条（需求理解 → 系分 → 测分 → 研发测试 Loop → 影响面 → 质量报告），状态色、当前节点、待办数、token / 成本。
- 待办（Attention）：所有等人处理的事项（审批、回答、判决交人），可以直接处理。
- 汇总：进行中 / 已交付 / 阻塞的需求数，本周 token 和成本。

**需求页**
- 顶部阶段条；Tab：**公共产物**（按 kind 分类，版本切换，评论）/ **运行**（DAG 画布）/ **追溯**（AC 覆盖总览 + 追溯图）/ **度量** / **动态**（事件流）。

**运行页**：DAG 画布 + 节点抽屉（见 03）。

## 度量（全部从事件日志计算）

| 指标 | 口径 | 用途 |
|---|---|---|
| 首跑可用率 | 首轮执行就通过的用例 / 全部可执行用例 | 生成质量 |
| Loop 轮次 | loop 节点的迭代次数 | 收敛速度 |
| 人工介入次数 | human.answered + 门禁人工放行 + 判决交人 | 自动化程度 |
| 判决分布 | 各 VerdictCategory 的数量 | 找上游问题：哪类失败最多就先治哪类 |
| 判决准确率 | 人工复核一致 / 已复核 | 判决 Agent 是否可信 |
| 守卫违规 | guard.violation 次数 | Agent 是否越权 |
| token / 成本 | harness.usage 汇总，按角色 / harness / 节点拆分 | 成本归因 |
| 交付周期 | 需求创建到准出 | 效率 |
| AC 覆盖 | 每条 AC 的用例数和通过情况 | 准出依据 |

**口径提醒**：调度完成（COMPLETED）≠ 业务通过（PASS）。所有"通过"都以门禁和用例结论为准，不以节点 succeeded 为准。
