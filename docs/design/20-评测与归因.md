# 20 · 评测与归因

## 解决什么问题

流水线交付的功能上线后出了问题，要能回答三件事：

1. **哪个环节引入的**：需求没写清、设计错了、代码写错了，还是测试设计漏了场景？
2. **哪个环节本该拦住却漏了**：评审看过但没发现、门禁没有这项检查、用例覆盖了但断言写错、判决分错了类？
3. **改了之后是不是真的变好**：改了某个技能、prompt 或模型，凭什么说比原来好，有没有把别的地方改坏？

现有能力能还原"发生了什么"：产物溯源（derivedFrom / producedBy）、哈希链事件、追溯图、评审记录。但还缺三样东西：

- **执行身份**：不知道某次节点执行用的是哪个版本的技能、prompt、模型；
- **缺陷归因**：交付后发现的问题没有录入口，也没有把它沿溯源链归到具体环节的手段；
- **评测手段**：没有办法把一个节点"冻结输入、换个版本重跑、打分对比"。

没有这些，出了问题只能凭感觉改 prompt，改完也不知道效果。

## 设计

### 1. 执行身份（配方）

每次执行 agent / review / judge / planner 节点和 rubric 门禁时，记一条 `node.recipe` 事件，内容包括：

- workflow 的 id、版本与源码修订；
- 节点 id、角色，角色档案的哈希；
- prompt 模板的哈希（动态 prompt 取函数源码的哈希）；
- 实际加载的技能清单：每个技能的名字和内容哈希；
- harness、模型、effort；
- 本次召回的经验 id。

除经验外的字段合起来算出 `recipeKey`。之后所有指标都能按"同一个节点的不同配方"分组。某个技能改了一版、某个角色换了模型，前后对比一目了然。

### 2. 节点成绩单（在线，零 token）

从事件和产物里直接算，按 workflow 节点、配方、技能三个维度聚合：

| 指标 | 口径 |
|---|---|
| 一次通过率 | 第一次执行就成功且完成标准全部满足 |
| 评审负担 | 该节点产物需要的评审轮数、打回次数、每个版本的 blocker / major 问题数 |
| 人工改写率 | 产物被人修改的比例，区分措辞调整和语义变更 |
| 自检质量 | 完成标准未满足次数、失败指纹被抑制次数 |
| 下游归因 | 沿溯源算到该节点头上的判决：case_defect 记到测试设计、script_defect 记到自动化、product_bug 记到开发、requirement_gap 记到 PRD |
| 逃逸缺陷 | 交付后被确认归因到该节点的缺陷数（见 3） |
| 成本 | token、时长 |

评审 / 门禁节点另算**检出率** = 它拦下的问题 ÷（拦下的 + 后来归因为"它漏掉"的逃逸缺陷）。

**技能成绩单**：加载了某技能某个版本的执行，与没加载或上一版本的执行对比上面这些指标。技能更新后指标明显变差时，在评测页标出"疑似退化"。

### 3. 缺陷逃逸归因

- **录入**：交付后发现的问题通过 Web、`takt defect report <REQ>` 或命令注册表的 `defect.report` 录入，也可以关联外部缺陷单链接。存为需求存放区里的 `defects/<id>.md`，并记事件。
- **确定性预检**（不花 token）：
  - 缺陷关联的 AC 有没有用例；
  - 用例最近一次执行的证据；
  - 涉及的代码文件是哪个任务节点改的（worktree 分支上的提交对应到节点）；
  - 这些产物经过了哪些评审、门禁。
- **归因 Agent**（独立角色 `auditor`，与任何产出角色不同）读缺陷和预检结果，沿溯源链读各环节产物，输出 `DefectAttribution`：
  - `introducedAt`：在哪个节点、哪个产物版本引入，属于需求 / 设计 / 实现 / 测试设计 / 自动化 / 环境 / 外部哪一类，附证据；
  - `missedBy`：本该拦住的环节，每项给出原因：
    - 没有覆盖；
    - 覆盖了但断言错；
    - 评审看过但没发现；
    - 缺这项门禁；
    - 判决分错了类；
    - 证据已过期。
  - `suggestions`：改进建议。目标限定为某个技能、prompt、完成标准、评审侧重点、门禁检查、经验或知识，每条写清改什么。
- **人确认**：归因要由人确认或修改（留痕），确认后才计入成绩单和检出率。
- **回归用例**：确认后的缺陷自动变成相关节点的回归评测用例，见下节。

### 4. 回放评测（离线）

- **评测用例**（`evals/<目标>/<用例>.json`）：
  - 冻结的输入：产物版本的内容快照，取自对象存储；
  - 被测节点的定义快照；
  - 判分规则：
    - 确定性检查：schema、完成标准由独立 verifier 核对、命令；
    - rubric：用不同于被测模型的模型打分；
    - 参考答案：经评审和人工修改后的最终版本；
    - 已知缺陷：必须指出 / 不得引入。
- **用例从哪来**：
  - 自动收集：历史上产物被评审打回或被人改过的节点执行，最终通过的版本作参考；
  - 确认过的逃逸缺陷，生成回归用例；
  - 技能自带的 `skills/<name>/evals/*.json`；
  - 人工编写。
- **运行**：`takt eval run <节点或技能> --variant <覆盖项>`。覆盖项可以是技能目录、prompt 文件、模型、harness。
  - 每个用例在沙箱里用冻结输入单独跑一次被测节点（复用临时任务的单节点 workflow），按规则打分；
  - 产出 `EvalReport`：每个用例的通过与否、分数、成本、时长；
  - 与基线配对比较：胜、负、平的数量，通过率与平均分的变化，回归用例有没有挂。
- **采纳门槛**：修改技能或 prompt 时（workflow 修改提议或技能文件保存），附上评测报告。默认只展示不强制；空间可以配置为"回归用例全过且通过率不低于基线"才允许保存。

### 5. 优化闭环

```
逃逸缺陷 → 归因（人确认）→ 改进建议 → 生成变体（改技能 / prompt / 完成标准 / 评审侧重点 / 门禁）
        → 回放评测（基线 vs 变体，含回归用例）→ 人批准 → 采纳（提交记录附评测报告）
        → 成绩单按配方监控前后变化
```

- **软层**：经验库（docs/design/19 第 11 节）可以自动学、自动试用；
- **硬层**：技能、prompt、门禁这类改动必须有评测证据并经人批准；
- **判决评测**：人工复核过的判决也进评测集，度量页展示判决混淆矩阵（docs/design/05）。

### 6. 界面

- **评测页**（空间级）：
  - 节点成绩单：可排序，配方版本的趋势小图，退化标记；
  - 技能成绩单；
  - 评测运行列表；
  - A/B 对比视图：逐用例的胜 / 负 / 平，点开看两边输出与打分理由。
- **需求页"缺陷"Tab**：录入缺陷；归因链可视化（在阶段条和追溯图上标出"引入"与"漏检"的位置）；确认 / 修改归因。
- **节点抽屉"配方"**：本次执行的技能版本、prompt 哈希、模型；链到该节点的成绩单。

## 不做什么

- 不自动采纳任何技能或 prompt 的修改；
- 不做显著性检验之外的复杂统计，先给配对胜负与区间；
- 归因 Agent 的结论只是候选，必须人确认才计数。

## MVP 范围

执行配方记录、节点与技能成绩单、缺陷录入与归因（确定性预检 + 归因 Agent + 人确认）、回放评测（agent 节点；确定性检查 + rubric + 参考答案对比）、技能自带评测用例、A/B 对比报告、对应的 CLI 与 Web 页面。放在 M3 第二批，与接入任务一起做；引擎里的配方记录等第一批引擎改动合入后再加，避免冲突。
