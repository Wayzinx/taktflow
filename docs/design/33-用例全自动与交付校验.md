# 33 · 用例全自动：只有 API 与 UI 两类，交付校验不再卡在手工用例

> 状态：设计中（2026-11-10 修订）。起因：标准交付流水线的一次真实运行（坦克大战需求）在「交付校验」连续失败两次后停下等人，提示「存在无用例、未通过或缺少证据的 AC」。实际上每条 AC 都有用例，70 条自动化用例全部通过，卡住的是 14 条「手工用例」。
>
> 修订说明：初稿把手工用例当成合法类别，打算放到人工准出里补做，还加了「交给 agent 判断」一类。这和全自动交付相违背，已撤回，改为从源头禁止。

## 1. 结论

- **全自动流水线里不应该有手工用例。** 用例只有两类：
  - `api`：调用接口、执行命令或读取文件，用程序断言结果。
  - `ui`：用浏览器打开页面，按键或点击，断言 DOM、画布、Console 和网络请求。
- **自动化不了的场景不写成用例**：比如主观体验、性能、故障注入、真实上下游数据。它们写进测分的「不覆盖 / 专项」清单，由专项测试负责，不做假覆盖。
- **这次的 14 条手工用例是几处一起漏出来的**：
  1. 测试设计的角色说明留了「标为不可自动化」的口子。
  2. 测分 agent 不知道流水线能驱动浏览器，就把界面检查写成了「Chrome + DevTools 人工看」。
  3. 测分评审和追溯对齐都不检查用例类别。
  4. 后来的修复（8f08cdb）反而把 `manual` 写进了脚本提示，等于把这个口子合法化了。
- **这 14 条其实都能自动化**：
  - 11 条是界面检查，用浏览器脚本就能跑。已在交付出来的页面上实测过 TC-AC2-001 / 002、TC-AC3-004、TC-AC18-003 的断言，都能自动判定。
  - 3 条（git 检查、README 完整性、「不做什么」核对）用命令就能跑。
- **改法**：
  1. 源头只允许 `api` / `ui` 两类。
  2. 测分评审和追溯对齐两道关口拦截不合规的用例。
  3. 提供 `takt browser`，让 `ui` 用例能执行。
  4. 交付校验写清原因。
  5. 确定性的失败不自动重试。

## 3. 设计

### 3.1 用例只有 `api` / `ui`

- 用例 JSON 的 `automation` 字段必填，取值只能是 `api` 或 `ui`。
- **读取时兼容旧值**：
  - `auto`、`command` 当作 `api`。
  - `devtools`、`browser` 当作 `ui`。
  - `manual`、`auto+manual` 和其他值都不合法。
- 一条用例既要逻辑断言又要画面检查时，有两种写法：
  - 拆成一条 `api` 加一条 `ui`。
  - 整条按 `ui` 写，`ui` 脚本里也能读页面状态。
- 「README 是否完整」「不做什么是否真的没做」写成 `api` 或 `ui` 用例：
  - 解析 README 的章节，照 README 里的命令跑一遍。
  - 用代码检索和页面检查确认没有外部请求、没有存储写入、没有声音。
- PRD 自相矛盾时不写 `blocked` 用例：测分评审把矛盾退回产品裁决，并回写 PRD。

### 3.2 两道关口

- **测分**：测试设计的角色说明和 test-design 的提示只允许 `api` / `ui`，自动化不了的写进测分的「不覆盖 / 专项」。
- **测分交叉评审**：checklist 加两项：
  - 每条用例都标明 `api` / `ui`，并且能自动执行，没有手工用例。
  - PRD 中的矛盾已退回裁决，没有 `blocked` 用例。
- **追溯对齐门禁**：新增检查 `cases-automatable`，列出 `automation` 不合法的用例，有一条就失败，退回测分。这样在写代码之前就拦住，不会拖到交付校验。

### 3.3 `ui` 用例能执行：`takt browser`

- **零依赖**：使用本机已安装的 Chrome / Chromium / Edge，以无头模式启动，用 Node 自带的 WebSocket 走 DevTools 协议，不往被测仓库里装任何包。
- **能力**：
  - 打开页面、等待元素或条件、执行 JS、按键 / 输入 / 点击、截图。
  - 收集 Console 输出和网络请求列表。
- **两种用法**：
  - `takt browser run <script.mjs>`。
  - 通过环境变量 `TAKT_BROWSER_MODULE` 给出 ESM 模块的绝对路径，由 `run-cases.mjs` 引入。
- **浏览器不可用时**：`ui` 用例记 `error`，原因写「本机没有可用的浏览器」。失败判决会把它归为环境问题，转给人处理。

### 3.4 交付校验写清原因

- 每条 AC 的 `details` 增加 `reason`，取值：`failed` / `no_cases` / `not_automated` / `no_evidence` / `not_run` / `blocked`。
  - 一条 AC 有多种情况时，取最严重的：失败 > 无用例 > 未自动化 > 缺证据 > 未执行 > 等裁决。
- 状态归一：
  - `manual`、`manual_pending` 算未自动化，只会出现在老运行里。
  - `error` 算失败。
- `message` 按原因汇总，例如：

  > 12 条 AC 未通过：14 条用例未自动化（TC-AC1-001、TC-AC2-001 … 等 14 条）；1 条等裁决（TC-AC15-001）。

### 3.5 确定性的失败不自动重试

- 门禁失败时，记录输入指纹：用例文件、执行汇总、证据的版本号。
- 指纹和上次失败时相同：不自动重试，直接转人工。
- 人工请求的 `ask` 用门禁的具体提示，不再写「同样的失败已出现 2 次」。

### 3.6 已经有手工用例的老运行

- 交付校验按新规则报「未自动化」，并列出用例 ID。
- 是否继续由人决定。要继续的话，有两种做法：
  - 退回测分，把这些用例改成 `api` / `ui`，再重做自动化脚本。
  - 由人在门禁处做出决定。

## 4. 不做

- **不做手工用例清单和人工补测表单**：初稿 §3.4 的方案，已撤回。
- **不做「交给 agent 判断」的用例类别**：初稿 §3.3 的方案，已撤回。README 完整性、范围核对都能写成 `api` 用例。
- **不自动修改 PRD**：裁决回写 PRD 仍由产品角色完成。
- **不做通用的端到端测试框架**：`takt browser` 只提供用例脚本需要的最小能力。
