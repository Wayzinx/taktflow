# 01 · 竞品对比：spec-kit、BMAD、superpowers、Archon，和我们的原型 workflow

> 调研时间 2026-11-04。星数为当日快照。"未提及"表示只读了 README 和主要文档，没找到对应能力，不代表一定没有。

## 结论先说

- **spec-kit / BMAD / superpowers 是"方法论 + 提示词资产"**：规定 Agent 应该按什么步骤做，靠模型遵守。它们管"怎么想"，不管"怎么跑、怎么证明跑对了"。
- **Archon 是最接近的竞品**：YAML 定义 DAG、节点可以是 agent / bash / 等人、接 Claude Code / Codex / Pi、有事件日志和 Web 控制台。它管"怎么跑"。
- **我们的原型（浏览器导航助手的 browser-nav-sdlc workflow）强在"怎么证明跑对了"**：追溯链、一用例一证据目录、测试锁、多轮门禁、分诊 → 路由修复、完整性审查。但它绑死一个项目、只能在 Claude Code 的 Workflow 工具里跑、没有 UI。
- **taktflow 的位置**：把原型里验证优先的那一套做成通用引擎，补上 Archon 已经证明有用的运行时能力（DAG、多 harness、控制台），再加上它们都没做透的四件事：**需求级公共存放区、判决 Agent 路由修复、上下文可视化、存量项目知识层**。

## 一、三个方法论框架的流程

| | spec-kit（14.7 万★） | BMAD-METHOD（5.5 万★） | superpowers（31 万★） |
|---|---|---|---|
| 定位 | 规格驱动开发（SDD）工具包 | 敏捷 AI 驱动开发方法 | Agent 的工程方法论技能包 |
| 核心流程 | constitution → specify → plan → tasks → implement → converge（循环到 Converged） | Clarify → Plan → Build and verify → Learn and adjust；按复杂度裁剪 | brainstorming → git worktree → writing-plans → subagent 逐任务执行 + 评审 → TDD → code review → finishing branch |
| 角色 | 无显式角色 | analyst / pm / architect / ux / po / dev / review / qa 等 Agent 技能 | 无角色，按阶段触发技能 |
| 流程怎么定义 | 斜杠命令 + 模板；新增 Workflow：YAML 步骤、StepBase 插件、执行树、断点续跑、fan-out / fan-in | SKILL.md + `customize.toml`；`bmad-build-auto` 单票无人值守，外部 orchestrator（bmad-loop）派发多票 | SKILL.md；靠 session-start hook 强制"先查技能" |
| 用户项目里生成什么 | `.specify/memory/constitution.md`、`specs/<feature>/spec.md, plan.md, research.md, data-model.md, contracts/, tasks.md` | `_bmad/` 配置、`tickets.toml`、epic / story 文件、plan 文件（带 status：draft → ready-for-dev → in-progress → in-review → built → done / blocked） | `docs/superpowers/specs/`、按日期命名的 plans |
| 测试与验证 | checklist、analyze 一致性检查、converge 收敛判断；Bug 扩展：assess → fix → test | review 有 quick / thorough 两档；`qa-generate-e2e-tests`；测试架构（TEA）是独立模块（116★） | TDD 强制先写失败测试；verification-before-completion；systematic-debugging |
| 失败处理 | converge 循环 | build-auto 写终态，blocked 交人 | 调试技能 + 评审分级，Critical 阻塞 |
| 追溯 | spec → plan → tasks 文档链 | ticket → plan → status 链 | plan → task → commit |
| 多 harness | 30+ 集成（Copilot、Claude、Codex、Cursor…） | Claude Code / Codex 插件、Skills CLI | Claude / Codex / Cursor / OpenCode / Kimi / Gemini 等插件 |
| 存量项目 | how-to/existing-projects | `project-context`、`deep-recon`、`ingest` | 未提及 |
| UI | 无（文档站） | 无（文档站） | 无 |
| 扩展机制 | Extension / Preset / Workflow step / Bundle / Catalog | 模块（bmod）+ toolsmith | 写技能（writing-skills） |

## 二、和我们最像的 Archon（2.4 万★）

| | Archon | 差距 / 我们要补的 |
|---|---|---|
| 流程定义 | YAML DAG：prompt / bash / script / loop（`until_bash`）/ wait（等人）/ 子 workflow / when 条件 | 我们用 **TypeScript 代码**定义：可复用函数、类型检查、planner 动态展开有边界 |
| 运行时 | 每次运行一个 git worktree；SQLite / Postgres 持久化；队列；attention 队列 | 相同方向；我们 MVP 用文件存储，后续加 SQLite 索引 |
| 执行内核 | Claude Code、Codex、Pi 作为 provider | 相同；我们加 DeepSeek Harness，并按角色和节点选 |
| 审计 | 事件日志、transcript、每次运行成本 | 我们加**哈希链**防篡改、产物溯源、需求级追溯图 |
| SDLC 包 | intake → build queue（plan / implement / review / fix / CI）→ merge queue → discoveries | 偏"issue 到 PR"；**测试设计、用例与证据、失败判决路由**未提及 |
| 公共物料 | 未提及（以 issue 为单位） | **需求级公共存放区**：PRD、会议纪要、设计稿、spec、用例、报告分类存放、带版本和评论 |
| 上下文 | `fresh_context` 选项 | **上下文账本**：每个节点注入了什么、多少 token、何时压缩、丢了什么，可视化 |
| 存量知识 | 未提及 | **知识层**：rg / Wiki / CodeGraph / DB / 接口注册，按问题类型路由 |
| UI | Web 控制台（`archon serve`）、Slack / Telegram | DAG 画布 + 需求阶段条 + 产物 Tab + 节点抽屉（产物 / trace / 上下文 / 判决），产物可在线改并触发下游重跑 |

## 三、逐项对比我们的原型 workflow

原型是 [Wayzinx/browser-nav-assistant](https://github.com/Wayzinx/browser-nav-assistant) 的 `.workflow/browser-nav-sdlc.workflow.js`（7 个阶段，约 1000 行）。

| 维度 | 原型做法 | 好的地方 | 不足 | taktflow 怎么做 |
|---|---|---|---|---|
| 阶段 | 需求与 PRD → 技术方案 → 用例设计 → 对齐与冻结 → 脚本与开发 → TDD 闭环 → 交付验收 | 覆盖完整，测试前置（先冻结用例再开发） | 阶段写死在一个脚本里 | 阶段 = StageDef，节点挂到阶段上；默认模板沿用这 7 段 |
| 流程定义 | Claude Code Workflow 工具的 JS 脚本 | 代码即流程、可控、可 resume | 只能在 Claude Code 里跑；无类型；无可视化 | 独立引擎 + TS DSL，CLI 和 Web 都能跑和看 |
| 角色 | PM / BE / FE / ARCH / TEST / AUTO / DEV-BE / DEV-FE / HUMAN，每个角色有负责的文件 | 职责和写权限清楚 | 写权限靠提示词约束 | AgentProfile.writeScope + 节点结束后 diff 守卫，越界自动还原 |
| 跨角色沟通 | 看板（`docs/trace/board/<ID>.json`），按"PROBLEM > PRD > 契约 > 用例 > 脚本"裁决 | Agent 之间不聊天，靠结构化记录 | 只在本项目内 | 看板记录变成公共存放区的 `decision` 产物，带评论和状态 |
| 追溯 | REQ → F（含 AC）→ C（`@code`）→ TC → evidence → 测试报告 | 链条完整 | 只有 JSON，没有图 | 追溯图 API + Web 视图；AC 覆盖总览 |
| 证据 | `evidence/<CaseID>/`：result.json、api/、server.log、extension.log、截图、gif、state diff | 一次执行全部证据 | — | 保留，作为 `evidence` 产物，判决 Agent 直接读 |
| 测试锁 | 冻结基线 → digest → 改动后完整性审查 → 违规还原 | 防"改测试换通过" | 规则在提示词里 | 守卫 + validator 写成代码（V1–V6，见 05） |
| 失败处理 | 分诊 → BE / FE / CORE / UI_SCRIPT_SUSPECT / API_TEST_SUSPECT → 修复 / 仲裁 / UI 探索 | 有归因、有路由 | 类别和产品耦合；没有判决评测 | 通用 VerdictCategory + 路由表 + 修复分级 + 判决准确率统计 |
| 引擎选择 | 开发 → Codex；测试 → worker；不可用时降级 | 按角色选引擎 | 写死在提示词里 | HarnessSelector + fallback 链，配置化 |
| 会话与上下文 | journal（≤60 行）+ sessions + briefs | 落盘续跑 | 看不到上下文构成 | 上下文账本 + 压缩记录 + Web 可视化 |
| 存量知识 | 无（新项目） | — | — | 知识层（08） |
| 项目管理 | 无 | — | — | 项目总览与度量（11） |

## 四、我们的定位

> **验证优先、证据驱动的 AI 交付流水线。**
> 别人管"让 AI 写出来"，我们管"让 AI 写出来的东西每一条都能追到需求、用例、证据和判决，交付时直接出可审计的准出报告"。

可以和 spec-kit 互补：spec-kit 的 spec / plan / tasks 产物可以作为公共存放区的输入，我们负责后半段的执行、验证和交付。
