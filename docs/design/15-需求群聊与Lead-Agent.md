# 15 · 需求群聊与 Lead Agent

## 解决什么问题

流水线跑起来以后，人想做的事情往往不在 DAG 里：问一句"现在到哪了、卡在哪"，让 AI"把 spec 第 3 条改成……""这个按钮文案改一下"，或者拉产品、研发进来讨论一个判决。这些事需要一个**对话入口**，并且对话里发生的修改也要留痕、可追溯。

## 设计

每个需求创建时自动开一个**需求群**：

| 成员 | 说明 |
|---|---|
| 真人 | 默认是需求负责人；空间成员可以被拉进来 |
| Lead Agent | 每个需求一个，"项目经理 + 调度员"，不亲自写代码 |
| 子 Agent | 被 Lead 派发任务时临时出现在群里，汇报进度和结果 |

群里的消息类型：文本、系统消息（阶段变化、运行结束）、待办卡片（审批 / 回答，可在群里直接处理）、任务卡片（子任务的状态与产物）、产物引用。

## Lead Agent 怎么工作

**触发**：有人 @Lead，或者给 Lead 发私聊；引擎事件（阶段变化、待办产生、运行失败、运行结束）也会触发它发一条进度说明。

**每次触发都是一个新会话**，不靠长对话记忆：
1. 组装上下文：角色说明 + 需求状态快照（阶段、正在跑的节点、待办、最近判决、度量）+ 最近 N 条群消息 + 它自己维护的备忘 `requirements/<REQ>/lead-notes.md`；
2. 模型输出**一条回复 + 一组动作**（结构化 JSON）；
3. 服务端按策略校验每个动作后执行，结果回帖到群里，并写审计事件（actor 是 Lead，`onBehalfOf` 是发起请求的人）。

这种"动作 JSON"方式对任何 harness 都适用（包括 mock 和 native），动作由代码执行，权限可控。后续再提供 `takt mcp`（MCP 服务），让支持 MCP 的 harness 在会话里交互式查询。

**动作清单**：

| 动作 | 作用 | 限制 |
|---|---|---|
| `reply` | 回复群消息、@某人 | — |
| `dispatch_task` | 派发临时任务给某个角色（独立上下文）：说明、输入产物、要产出的产物、写权限、目标代码仓库 | 角色必须存在；写权限只能收窄 |
| `start_run` / `resume_run` / `cancel_run` | 启动、继续、取消流水线 | 取消需要发起人是 maintainer 以上 |
| `request_human` | 向某人发起待办（审批 / 回答） | — |
| `propose_workflow_change` | 提出对 workflow 的修改（自然语言说明 + 可选补丁），生成待审批的修改 | 不能直接改，必须人批准 |
| `update_notes` | 更新 lead-notes.md | — |

**Lead 不能做的**：替人审批、绕过评审改基线产物、直接写代码。所有"改东西"都通过派发任务完成，任务就是一次普通的运行（单节点或"实现 → 评审"小流程），在运行列表和追溯图里都看得到。

## 临时任务（ad-hoc task）

`dispatch_task` 生成一个任务运行：`task` 类型的小 workflow（默认 `agent → review`，评审可关），复用全部引擎能力：写权限守卫、上下文账本、产物版本、哈希链。任务卡片在群里实时更新状态。

## 外部 IM

`ChatBridge` 接口：`createRoom / invite / post / onMessage`。先实现内置 Web 群聊；飞书、Slack 适配器后续按这个接口接入，消息双向同步，审计以 taktflow 侧为准。
