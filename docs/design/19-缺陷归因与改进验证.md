## 一、产品

### 1.1 要解决的两件事

现在能还原"发生了什么"：产物从哪来、被哪个节点生成，防篡改的事件日志、追溯图、评审记录。但出了问题之后：

1. **说不清是谁的锅**：需求没写清、设计错了、代码写错了、还是测试设计漏了场景？哪个评审或门禁本该拦住却漏掉了？
2. **证明不了改好了**：改了 Skill、角色档案或 prompt，没法证明它更好，也不知道有没有改坏别处。

两件事是一条闭环：**归因**把问题定位到"哪次调用、哪一版配方、当时看到了什么"；**评测**用归因沉淀的样本证明"新配方在冻结样本上更好、没有增加误报"。

### 1.2 分三期交付

| 期 | 能回答的问题 | 范围 |
|---|---|---|
| **一期：文档评审闭环** | "这次文档评审漏掉了什么？当时用了哪些材料、哪版配方？换配方后在冻结样本上是否改善，误报有没有变多？" | 公共存放区里的**文档类评审**（PRD、系分、测分的 review 节点）；每个评审者调用的配方与输入冻结；评审观察自动入账、人确认缺陷；归因页展示版本差异与候选生产调用，**人确认**引入点与漏拦点；确认的缺陷收录为评测样本；**单个评审者调用**的新旧配方回放与对比报告 |
| **二期：代码与测试** | "这个用例失败，是需求、设计、代码、用例还是脚本的问题？哪个评审或门禁该拦？" | 代码类产物的调用级溯源（提交身份、前后状态）；judge / gate 的观察入账（gate 有 pass / fail / error）；归因 Agent **给建议**（不自动确认）；门禁与判决的漏拦状态；跨运行合并建议；质量页矩阵与逃逸率（带口径说明） |
| **三期：改进验证与发布门槛** | "这次 Skill 改动能不能发布？" | 节点重执行回放（作者 + 多评审者多轮、写代码节点在隔离沙箱里）；资产草稿 / 发布状态机与依赖索引；预先规定统计方法的发布门槛；按配方版本的趋势 |

### 1.3 用户看到什么（一期）

- **需求页"缺陷与归因"Tab**：本需求的评审观察与已确认缺陷；每个缺陷一张**归因卡**——发现点（哪次评审调用、哪个问题）→ 候选引入点（哪些产物版本的差异让它出现，附 diff）→ 当时的评审调用看到了哪些材料、职责是什么、结论是什么；每一项都可以点开原文；人确认 / 改判 / 标记"不是缺陷"。
- **评测页**：已收录的样本（含**无缺陷负样本**）；选一个评审角色的候选配方（例如改过的 Skill 草稿），对选中样本发起回放；报告给出每个样本两组的结果、误报变化、证据不足的项。
- **需求群（dsh）里问 Lead**："这次 PRD 评审漏了什么？""评审 Skill 改了之后在样本上表现如何？"——Lead 读归因与报告回答，区分"已确认"与"候选"。

### 1.4 原则与不做什么

- **证据优先**：每个结论都链接可核验的证据；证据不足就是 unknown，不猜。
- **人终审**：一期不自动确认任何归因；二期起 Agent 只给建议。
- **只归到流程环节和配方版本**，不做人员考核。
- **旁路**：归因和评测不影响正在跑的流水线；回放在隔离副本里执行，绝不写回真实空间。
- 不承诺自动修复规则或 Skill；不做整条流水线端到端回放。

## 二、技术方案

### 2.1 身份模型：recipe / invocation / inputSnapshot

```ts
/** 配方内容版本：只包含"可以复用、可以比较"的静态部分。相同配方 → 相同 recipeId。 */
interface Recipe {
  recipeId: string                       // sha256(canonical(下列字段))
  role: string
  profile: AssetRef                      // 角色档案（文件 / 插件内置 / 内存定义）
  skills: AssetRef[]                     // 声明使用的 Skill
  template: AssetRef                     // 节点 prompt 模板或评审职责（focus / checklist / rubric）的版本
  harness: string; provider?: string; model?: string; effort?: string    // requested 值
  outputSchema?: string                  // sha256
}
interface AssetRef { kind: 'file' | 'plugin' | 'inline'; id: string; sha256: string; revision?: string }

/**
 * 一次工作流 HarnessAdapter.run 尝试（不是一次模型请求：native 等 harness 内部可能有多轮模型请求，
 * 只计入 usage；available() 健康探测不记）。产物、评审结果、用量、会话、AgentTrace 都关联它。
 */
interface Invocation {
  invocationId: string                   // <runId>:<seq>，seq 取调用开始事件的序号
  runId: RunId; nodeId: NodeId; attempt: number; iteration?: number
  review?: { round: number; part: 'author' | 'reviewer'; reviewer?: string }
  gateCheckId?: string                   // rubric 门禁
  fallbackIndex: number                  // 第几个候选 harness
  recipeId: string
  inputSnapshotId: string
  resolved: { harness: string; model?: string; effort?: string }       // 引擎解析后
  reported?: { model?: string; sessionId?: string }                    // harness 回报（不回报则缺省）
  outcome?: { status: 'ok' | 'error' | 'cancelled'; usage?: Usage }
  replay: 'full' | 'limited' | 'none'    // 见 2.2 的不可复现边界
}

/** 本次输入与最终请求的冻结快照（正文进 .takt/objects，先脱敏）。 */
interface InputSnapshot {
  inputSnapshotId: string                // sha256(canonical)
  request: { prompt: string; systemAppend?: string; schema?: string }   // object 引用
  inputs: Array<{ ref: ArtifactRef; sha256: string; object: string }>   // 提供给调用的产物正文
  knowledge?: Array<{ source: string; ref: string; object: string }>    // 命中正文
  skillsProvided?: AssetRef[]            // 实际提供给 harness 的技能目录内容清单
  cwdLayout: { root: string; paths: Record<string, string> }            // 回放时路径重映射
  /** 重组请求所需的全部材料：替换配方组件后能确定性地重新渲染。 */
  render: {
    rendererVersion: string                                             // 引擎 prompt 渲染器版本
    template: { kind: 'node-prompt' | 'review-reviewer' | 'review-author' | 'rubric'; object: string }
    params: string                                                      // 结构化参数对象（评审：被评审对象、参考依据、checklist、已有问题清单、轮次）
    assets: Array<AssetRef & { object: string }>                        // 角色档案、Skill、职责模板正文
    exec: { adapter: string; adapterVersion: string; tools: string[]; permissions: string; env: string[] }   // 工具 / 权限 / 环境变量名（不含值）
  }
  redactions: number                     // 脱敏处数；>0 时 replay 至少为 limited
}
```

- 记录点：引擎在 harness 请求组装完成后、`HarnessAdapter.run` 之前写 `invocation.started`（含 recipe、inputSnapshot），返回后写 `invocation.finished`（outcome、reported）。**只有真实发起 run 才记**：judge 无失败不调模型、纯规则门禁都不产生 invocation。
- review 节点：每个评审者每轮一个 invocation，作者每次修改一个 invocation；rubric 门禁每个检查项一个；fallback 每个候选一个。
- 存储：事件进运行哈希链；`.takt/runs/<id>/invocations/<invocationId>.json` 为可重建读模型。
- dsh 插件的 AgentTrace 增加 `invocationId`、`recipeId`（替代按 node / attempt 建模的唯一性），面板互相跳转。

### 2.2 采集契约（实际材料，而不是声称）

| 材料 | 记录方式 | 边界 |
|---|---|---|
| prompt / systemAppend / schema | 冻结交给适配器的最终请求正文 | 这是"交给 harness 的请求"，不等于模型最终输入（harness 可能再加系统提示）；标注 |
| Skill | `skills`=声明使用；`skillsProvided`=同步到 harness 技能目录后的**实际内容清单**（目录已存在而跳过同步的情况要计算实际目录内容 hash）；`confirmed`=harness 事件证明加载（dsh 的 skill 工具调用等），无法观测记 unknown | 不把空间源文件的新 hash 当成实际使用的内容 |
| 知识 | 命中片段正文进对象存储 | 回放时直接注入冻结片段，不重新检索 |
| 模型 / effort | requested（配方）→ resolved（引擎）→ reported（harness 回报） | 适配器不支持覆盖时（例如 dsh CLI 适配器不传 model / effort）标记"未生效"，不当成实际值 |
| 角色档案来源 | AssetRef：文件 sha256 + 修订；插件内置 / 内存定义用插件版本 + 内容 hash | 不要求一律有文件路径 |
| workflow 源码 | 由加载入口传入源码与依赖闭包 hash，运行开始时冻结 | 不事后重读当前文件冒充历史版本 |
| 脱敏 | 新对象与已有 `harness.message` 走同一个脱敏器 | 脱敏改变了请求内容时 `replay: 'limited'`，报告里显式列出 |

### 2.3 调用级溯源

现有溯源（`derivedFrom`、`producedBy`、`traceIds`）只能给出部分候选链：`producedBy` 没有 attempt；同内容写入复用旧版本；结果依赖（`ctx.resultOf`）不进溯源；`traceIds` 是当前记录而非历史版本；review 作者修改后以原节点身份保存。新增：

- **产物关系事件** `artifact.touched`：`{ invocationId?, nodeId, attempt, ref, relation: 'produced' | 'reused' | 'modified', previous?: ArtifactRef }`——内容去重照旧，但每次执行对产物的生产、复用、修改都留一条。
- **结果依赖**：节点读取上游结构化结果（`resultOf`、judge 的 target 结果）时记录 `{ from: { runId, nodeId, attempt } }`，进本节点 invocation 的输入。
- **历史追溯 ID**：从指定版本正文提取（AC-* / TC-*），不用当前记录的 `traceIds`。
- **代码**（二期）：写代码调用前后的 worktree 状态（基线提交、未提交 / 未跟踪文件 hash）、产生的提交 SHA 与改动文件，索引为 `{ commit → invocationId }`。

### 2.4 观察记录与缺陷

两层模型：

```ts
/** 不可变的观察记录：某个来源在某个时刻对某个对象说了什么。按源事件幂等入账。 */
interface Observation {
  id: string                              // 幂等键：<source>:<runId>:<seq>:<itemIndex>
  source: 'review' | 'judge' | 'gate' | 'human' | 'external'
  kind: 'found' | 'claimed_fixed' | 'verified_fixed' | 'declined' | 'overridden' | 'error' | 'flaky' | 'ignored'
  invocationId?: string; runId?: RunId; nodeId?: NodeId; attempt?: number; round?: number
  subject: { artifact?: ArtifactRef; testCase?: string; checkId?: string; location?: string }
  issueKey?: string                       // 系统管理的问题身份（2.5）
  severity?: 'blocker' | 'major' | 'minor' | 'nit'
  text: string; evidence: string[]
  at: Timestamp
}

/** 缺陷实体：聚合多个观察记录；由人确认（二期起可由建议 + 人确认）。 */
interface Defect {
  id: string                              // DEF-<REQ>-<n>
  requirementId: RequirementId
  title: string; severity: 'blocker' | 'major' | 'minor'
  observations: string[]                  // 关联的观察记录
  validity: 'unconfirmed' | 'valid' | 'not_a_defect' | 'duplicate'
  resolution: 'open' | 'claimed_fixed' | 'verified_fixed' | 'accepted_risk' | 'reopened'
  duplicateOf?: string
  attribution?: Attribution               // 2.6；人确认后才是 confirmed
  revision: number                        // 乐观并发：改判、合并都要带 baseRevision
}
```

- **逐调用落盘**：每个评审者调用完成即写 `review.result`（`{ checkpointId, invocationId, output: object, artifacts: ArtifactRef[], references: ArtifactRef[] }`），不等本轮其他评审者；某个评审者失败不影响已完成者的结果入账。
- **一期入账**：只从**文档评审**自动产生观察：每个评审者调用的每条问题一个 `found`；作者回应 `fixed` 记 `claimed_fixed`（作者自述，不等于已修）；评审者在下一轮对该 key 明确给出 `resolved` 才记 `verified_fixed`（"本轮没提"不算确认）；`declined` 记 `declined`；人工放行 / 轮次耗尽交人后通过记 `overridden`。缺陷由人从观察里确认创建（可一次选多条观察）。
- **二期入账**：judge 每个失败对象每次一条观察（`ignore` 路由记 `ignored`、`flaky` 记 `flaky`，不丢）；gate 增加执行状态 `pass | fail | error`，`error` 记为流程问题而非产物缺陷；外部 bug 导入为 `external`。
- **不自动按用例合并**：同一 TC 在不同轮次可能是不同根因，一个根因也可能导致多个 TC 失败。合并只给建议，人确认，可撤销。

### 2.5 问题身份（issueKey）

- 由**系统管理**：第一次出现时分配 `ISS-<n>`；后续轮次给评审者列出已有问题清单（key + 描述 + 状态），要求"引用已有 key 或声明新问题"；模型不能自造 key 格式。
- 评审输出 schema 增加 `previous: Array<{ key; status: 'resolved' | 'still_open' | 'not_checked'; note }>`：对清单里每个已有问题逐条给出复查结论。
- 同一 review 节点内跨轮有效；重做（rework）、loop 迭代、跨运行、不同评审者之间：系统只做**精确去重**（同一评审者引用同一 key），语义相似的给出**合并建议**，人确认。
- 现有 `ReviewIssue.id` 保留为轮内编号，新增 `ReviewIssue.key`（协议增量 R3）。

### 2.6 归因

一期全部**由人确认**；系统提供证据和候选：

1. **候选生产调用**：从缺陷关联的观察找到被评审产物版本，沿 `artifact.touched` 与 `derivedFrom` 列出该版本及其上游每一跳的生产调用（invocation、配方、当时输入）。
2. **版本差异证据**：对候选链上每个产物，给出"上一版本 → 被评审版本"的差异，并标出与缺陷描述相关的段落（一期用文本检索 + 人工；二期可加 Agent 建议）。
3. **引入点判定规则**：只有当某一跳的差异证明"此前不存在、此后出现"（或"此前正确、此后被改错"）时，才能确认为引入点；人工编辑不截断历史，人工版本也可能只是改了错别字。证明不了 → 候选列表 + `unknown`。
4. **归因记录**：

```ts
interface Attribution {
  status: 'candidate' | 'confirmed' | 'disputed' | 'unknown'
  category?: 'requirement' | 'design' | 'test_design' | 'code' | 'automation' | 'knowledge' | 'environment' | 'process'
  injected?: { invocationId?: string; artifact: ArtifactRef; previous?: ArtifactRef; human?: boolean; diffEvidence: string }
  escapes: Escape[]                       // 2.7
  candidates: Array<{ invocationId?: string; artifact: ArtifactRef; reason: string }>
  method: 'human' | 'agent_suggested'     // 一期只有 human
  rationale: string; evidence: string[]
  by: Actor; at: Timestamp; baseRevision: number
}
```

judge 分类（二期）只作为线索：代码不符合需求可能源于设计错误；按 05 的权威顺序（spec > 契约 > 用例 > 脚本 > 实现）组织候选。

### 2.7 漏拦判定

**检查点身份**：`checkpointId = <runId>:<nodeId>:<attempt>:<round>:<reviewer | checkId>`，在检查点被调度时就分配；执行了才有 invocation，未执行（出错、被跳过）的检查点也能被漏拦分析引用。

**检查点输入清单**：每个评审 / 门禁检查点冻结"提供给它的材料"——**被评审对象 + 参考依据**（产物版本 + 正文 hash），一期在调用前把这些版本**物化成只读快照**交给评审者（替代当前读工作目录可变文件），从而能声称"它看到的就是这些"。职责版本 = 评审的 focus / **checklist 条目** / rubric 的 AssetRef。

**标准流水线配套改动（一期）**：review 节点增加 `references`（比较依据：PRD 评审带澄清结论；系分评审带 PRD；测分评审带 PRD 与契约）和 `checklist`（每个评审者的职责条目，例如"每条验收标准都可验证""契约字段完整"）；`taktflow-standard` 模板按此补齐。没有 checklist 的检查点，漏拦只能判到 `undetermined`。

**状态**（`Escape.verdict`）：

| 状态 | 条件 |
|---|---|
| `should_have_caught` | 五项同时满足：① 缺陷在该检查点执行时已经存在（引入点早于它，且其输入版本包含缺陷段落）；② 相关材料在输入清单里；③ 属于该检查点明确列出的职责（checklist / rubric 条目可对应）；④ 检查确实执行完成；⑤ 输出里没有提出该问题 |
| `caught_but_overridden` | 检查点提出了该问题（同 key 或人确认同一问题），问题已被确认有效，随后被 `declined` 或人工放行 |
| `not_exposed` | 相关材料不在输入清单里 |
| `not_executed` | 检查点没有执行或执行出错 |
| `out_of_scope` | 职责里明确不包含此类问题 |
| `undetermined` | 以上都不能证明（不用 `out_of_scope` 吸收未知） |

`Escape` 记录 `{ checkpointId, invocationId?, runId, nodeId, attempt, round?, reviewer?, checkId?, humanRequestId?, verdict, rationale, evidence }`；`not_executed` 没有 invocationId。

### 2.8 质量存储与一致性

- **权威日志**：core 新增类型化的**空间质量日志** `.takt/quality/log.jsonl`（复用 FsEventStore 的哈希链与链尾锚点，事件类型白名单扩展），记录 `observation.recorded / defect.created / defect.updated / attribution.recorded / evalcase.* / eval.*`。缺陷、归因、评测集都是**从日志重建的读模型**（`.takt/quality/views/*.json` 可删可重建）。现有 server 侧空间审计（写通用 `log`）不作为质量事实源。
- **幂等与游标**：观察记录的 id 就是幂等键；旁路任务记录每个运行已处理到的事件 seq（`.takt/quality/cursors.json`）和处理器版本，重启后从游标继续。
- **提交**：查重（幂等键）、检查 `baseRevision`、追加事件、更新链尾锚点在**同一个提交锁**（质量日志文件锁）内完成；空间租约只管执行所有权，不承担并发控制（同 owner 也可能并发）。
- **游标**：质量事件提交成功后才推进对应运行的游标；崩溃后从游标重放，靠幂等键去重。
- **中断恢复**：日志已追加、锚点未更新（`verify` 报 `incomplete`）时，`takt quality repair` 在链完整的前提下补齐锚点并追加一条 `log.recovered`；链不完整（tampered / truncated）拒绝自动恢复，交人处理。
- **旁路任务**：冻结证据（读取并 hash 所需产物与事件）→ 分析 → 提交前检查缺陷 `revision` 未变，变了就重算；**人工确认 / 改判的结论不会被自动结果覆盖**；分析失败记 `pending / error`，可补算。
- **入口**：CLI 单次 `takt run` 结束时同步处理；常驻宿主（serve、dsh 插件）订阅事件；另有 `takt quality sync` 补算。写入在空间租约内进行。
- **写 API**：api-core 增加 `defect.create / defect.update（确认、改判、合并、标重复、改状态）/ attribution.record / evalcase.add / evalcase.retire / eval.start`，全部带 `baseRevision`，人 actor 带 `via`。

### 2.9 回放

**两个不同的东西：**

| | 调用回放（一期） | 节点重执行（三期） |
|---|---|---|
| 回放什么 | 一次调用：冻结的最终请求 + 输入快照，换候选配方组件（Skill、角色档案、职责模板、模型）后重新发起 | 整个节点：review 的作者 + 多评审者多轮状态机、写代码节点 |
| 需要什么 | `Invocation` + `InputSnapshot` + 配方覆盖规则 | 专用的可回放节点描述（完整定义、状态、上下文、代码前后状态），不使用展示用的 SnapshotNode |
| 一期支持 | **单个只读评审者调用** | — |

**隔离是回放的前置条件**（WriteGuard 是事后比较、默认 local 没有文件系统隔离，不能当作隔离）：

- 一期唯一验收执行环境：**dsh 子 Agent**。回放用的角色 preset 不加载任何写工具和 shell（`dsh-tool-fs` 的 write / edit 关闭），读守卫限定在本样本的快照目录；不能访问正式空间、`.takt/quality/**`（评测期望）和其他样本。
- 启动前校验：preset 工具清单、读守卫范围、快照目录权限；任一不满足**拒绝启动**并说明原因。其他 harness（codex、claude-code 等）只有在 bwrap / docker 等经过验证的隔离环境下才允许回放，一期不验收。

**候选包**（一期替代"草稿"，不依赖三期的发布状态机）：

```ts
interface Candidate {
  candidateId: string                       // sha256(canonical)，不可变
  replaces: Array<{ asset: AssetRef; content: string /* object */ }>   // 替换的角色档案 / Skill / checklist 正文
  params?: Record<string, unknown>          // 结构化评审参数的覆盖（例如 checklist 条目）
  exec?: { model?: string; effort?: string }
  createdBy: Actor; note: string
}
```

存在 `.takt/quality/evals/candidates/<candidateId>/`，只用于实验，**不写回正式空间**；报告绑定 candidateId。正式发布仍走现有编辑（直到三期发布状态机）。

**调用回放的执行**：

- 每个样本独立的临时 workspace / stores / 会话；按 `cwdLayout` 重映射路径；材料以只读快照提供。
- 重新渲染：用 `render` 里冻结的模板、参数、资产，按候选包替换对应组件后用同一 `rendererVersion` 渲染；渲染器版本不同或缺资产正文时拒绝并标注；`replay: 'limited'` 的调用报告里标注。
- 不支持的情况明确拒绝：含函数的动态 prompt 无法从冻结请求重建时只允许"同模板换模型"；依赖外部服务的调用标记不可复现。

### 2.10 评测：样本、评委、结论

```ts
interface EvalCase {
  id: string; revision: number
  kind: 'must_catch' | 'clean'            // clean = 无缺陷负样本，约束误报
  origin?: { defectId?: string; invocationId: string }
  target: { role: string; template: AssetRef }          // 一期：某个评审角色的某类评审
  frozen: { invocationId: string; inputSnapshotId: string }
  expectation:
    | { kind: 'must_catch'; issue: string; issueKey?: string }
    | { kind: 'clean'; allowedSeverities: Array<'minor' | 'nit'> }   // 不应提出 blocker / major
  status: 'proposed' | 'active' | 'retired'
}
```

- **样本来源**：确认的缺陷且有 `should_have_caught` 漏拦点 → 提议 `must_catch` 样本（冻结那次漏拦的评审调用）；人确认无问题的文档评审调用 → 可收为 `clean` 样本。人或 Lead 收录。
- **评委**：评测集修订、期望、评委配方、判分规则都冻结在实验里；两组用同一评委；对评委隐藏组别、随机展示顺序；评委也记 invocation。
- **结论**：每个样本每组 `pass / fail / insufficient`（环境错误、无法回放、评委无法判定、零适用样本都不算通过）；`clean` 样本上提出 blocker / major 记误报。
- **报告**：按样本配对比较（同一样本两组各 N 次）；展示每样本通过次数、Wilson 区间（仅展示）、误报次数；**一期 N 默认 3，报告标明"探索性，不作为发布证明"**；结论仅限评测范围内。

### 2.11 发布状态机（三期前置）

- Skill / 角色档案 / 职责模板 / workflow：不可变的**资产修订** + 独立的 **published 指针**；运行冻结实际采用的修订（已在 2.2 记录）。现有 workflow-source 保存即替换、Skill 编辑直接写文件的行为需要先改为"保存修订 → 发布指针"。
- **依赖索引**：配方组件 → 使用它的 invocation 与评测样本，用来选影响面；零覆盖时明确提示"没有样本覆盖，无法评估"。
- 发布前校验：报告对应的候选修订、基线、评测集修订、评委、规则版本仍然一致；评测后再改的草稿不能复用旧报告。
- 发布门槛：预先规定的比较方法、允许退化幅度、最少样本数与复测预算（三期另行设计，不用 N=3 判定）。

## 三、一期实施与验收

**先行（调度方）**：冻结本节协议（类型、事件、api-core 操作）、唯一验收执行环境（dsh 子 Agent）、目录归属。

| 批次 | 任务 | 目录 | 内容 |
|---|---|---|---|
| 第一批（并行） | A 存储 | `core/store/**` | 质量日志（类型化事件、提交锁、锚点、repair）、读模型与重建、游标、评审材料只读快照物化、候选包存储 |
| | B 引擎采集 | `core/engine/**`、`templates/**` | invocation / recipe / inputSnapshot（含 render）采集；review 逐调用落盘、checkpointId、issueKey 与逐 key 复查 schema、references / checklist；`artifact.touched` 与结果依赖（文档）；标准模板补 references 与 checklist |
| | C 回放执行环境 | `harness/**`（及 dsh 插件仓库） | 只读评审回放的隔离校验；dsh 插件侧：回放 preset、读守卫限定快照目录、启动前校验 |
| | D Web | `web/**` | 需求页"缺陷与归因"、评测页（按冻结 API，先用 mock） |
| 第二批 | E 接入 | `server/**`、`cli/**` | api-core 读写操作；观察补算（run 结束同步 + `takt quality sync` + `takt quality repair`）；人工确认 / 改判 / 合并 |
| | F 归因读模型 | `core/insights/**` | 候选生产调用、版本差异证据、漏拦状态计算 |
| 最后 | G 回放与报告 | `core/quality/**`（新） | 样本收录、调用回放编排、固定评委、探索性报告；真实闭环验收 |
| 宿主（dsh 插件仓库） | H | `taktflow-dsh` | AgentTrace 关联 invocationId / recipeId；`takt_trace why / defects`；面板透出质量操作 |

Q1 的强制验收限定为**文档生产者、修改作者、评审者及其 fallback**；其他节点复用同一采集钩子但不进一期验收。

**验收（以证据正确性为准）：**

- 文档生产者、修改作者、评审者及其 fallback 的每次 `HarnessAdapter.run` 都有 invocation 记录；同一配方在不同运行得到相同 recipeId；不发起调用的节点没有虚假记录；评审者失败时已完成评审者的结果仍然入账。
- 归因卡上的每一条结论都能点开证据原文；系统不自动确认任何归因；证据不足时显示 unknown 与候选列表。
- 构造场景（PRD 漏写验收标准、系分契约字段错、测分漏边界、评审该拦未拦、评审拦住被放行、材料没提供给评审、重复问题、证据不足）只做**功能验收**；另外统计人工标注下的**错误归责率**（确认结论与标注不符的比例）和 **unknown 比例**，分开报告。
- 回放：用原配方回放原调用，请求在路径重映射后与原请求等价；`limited` 项被正确标注；clean 样本能测出误报变化。
- 真实 dsh 上：跑一次带文档缺陷的标准流水线 → 观察入账 → 人在面板确认缺陷与归因 → 收录样本 → 改一个评审 Skill 草稿 → 回放出报告。

## 四、风险

| 风险 | 应对 |
|---|---|
| 把溯源当因果 | 引入点必须有版本差异证据；人终审；unknown 是正常结果 |
| 评审"看到的材料"不可证 | 一期物化只读快照；做不到的检查点只能声称"提供了哪些版本" |
| 问题身份漂移导致重复或错误合并 | 系统管理 key；只精确去重；语义合并只建议 |
| 小样本误判 | 一期报告标明探索性；发布门槛三期另行设计 |
| 评委偏差 | 固定评委、盲评、负样本；客观项优先 |
| 回放保真度 | 冻结最终请求与输入；脱敏或外部依赖导致的受限显式标注 |
| 成本 | 回放预算上限；只跑选中的样本；样本数可调 |
| 用于人员考核 | 只归到环节与配方版本 |
