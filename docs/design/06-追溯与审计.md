# 06 · 追溯与审计

## 解决什么问题

"AI 10 分钟写完，没人 review，也不知道为什么这么写"——黑盒化。需要做到：

1. **任何一个产物都能回答"从哪来、谁做的、基于什么"**；
2. **任何一个需求都能回答"每条验收标准有没有被验证、证据在哪"**；
3. **任何一次运行都能完整回放，且事后不能被悄悄改**。

## 三张表

| 记录 | 位置 | 回答什么 |
|---|---|---|
| 产物溯源 | `workspaces/<REQ>/manifest.json` 的 `versions[].derivedFrom / producedBy / author / reason` | 这个版本基于哪些输入、哪个节点产出、谁改的、为什么改 |
| 事件日志 | `runs/<RUN>/events.jsonl` | 运行里发生的每件事：节点开始结束、工具调用、门禁结果、判决、人工决定、守卫违规、上下文组装与压缩 |
| 追溯图 | 读模型，按需计算 | 需求 → AC → 用例 → 脚本 → 证据 → 判决；spec → 任务 → 代码改动 |

## 追溯 ID

沿用原型的 ID 链，但不强制格式，只要求出现在产物内容或文件名里，引擎用正则抽取进 `traceIds`：

`REQ-001` → `AC-001-03`（spec 里的验收标准）→ `TC-API-RULE-042`（用例）→ `evidence/TC-API-RULE-042/` → 判决 → 质量报告

Web 的需求页给出**验收标准覆盖总览**：每条 AC 的用例数、通过、失败、异常，未覆盖的给原因。

## 防篡改：哈希链

每条事件：`hash = sha256(prevHash + canonical({seq, ts, runId, nodeId, type, actor, data}))`。`takt audit verify <runId>` 从头算一遍，返回第一处断链。产物版本是内容寻址的，改内容必然改 sha，manifest 里的历史不会丢。

这不是密码学意义上的强防护（有写权限的人可以整链重算），但能防"悄悄改了某一条"，配合 git 提交就足够审计。

## 人工修改

- 人可以在 Web 或 CLI 改任意产物，必须写原因；
- 修改产生新版本（author = human），记 `artifact.edited` 事件；
- 读过旧版本的节点及其下游标 `stale`，画布上显示影响面，人决定重跑哪些。

## 度量从审计里来

所有度量（首跑可用率、Loop 轮次、人工介入次数、判决分布、token 和成本）都从事件日志计算，不另外埋点，保证"数是对得上的"（AI 交付平台的度量都应该这样：流水线做的每件事都可统计）。
