# 23 · 知识库体系

## 解决什么问题

[08](08-存量项目知识层.md) 定了"先按问题类型路由，再渐进式披露"，也实现了 grep / wiki / workspace / git-history 四个源。真用起来，问题有四个：

1. **只能改配置文件**：知识源登记在 `takt.config.json` 的 `knowledge` 里，页面只能看，不能从零新建或构建一个知识库。
2. **类型不全**：没有向量 / 混合检索，没有"从代码仓库生成 LLM Wiki"，数据库和接口只有空实现。
3. **没有生命周期**：不知道知识库建没建好、是不是过期了、哪个版本在用，也没有构建进度和日志。
4. **不知道有没有用**：没有召回评测，改切块或检索参数靠感觉；有了 `knowledge.query` 事件，也没人去看哪些查询失败了。

## 类型

| 类型 `kind` | 适合回答 | 数据从哪来 | 构建 | 查询 | 新鲜度 |
|---|---|---|---|---|---|
| `rag` 文档检索 | 业务规则、产品文档、规范 | 上传文件、仓库路径（glob）、URL | 解析 → 切块 → 嵌入（可选）→ 索引；按内容哈希增量构建 | 混合检索：BM25 + 向量，RRF 合并，可选 rerank | 源变化或定时触发重建 |
| `llm-wiki` 基于 git 的 Wiki | 模块职责、业务流程、"为什么这么设计" | 一个 git 仓库或目录里的 markdown；可以由 Agent 从代码仓库生成 | 生成：大纲 → 逐模块成页 → `index.md` → 人审；增量：按 commit diff 重写受影响的页面 | 导航式：index → 模块页 → 段落，加关键词和别名 | 由 commit 驱动；每页记录 `sources`、`verifiedAt` |
| `database` 数据库 | 表结构、字段口径、真实数据 | 只读连接（postgres / mysql / sqlite） | 抓结构快照（表、列、注释，样例行可选）→ 建结构索引；可以给字段标注口径 | 两步：先在结构索引里找表，再生成 SQL → 只读守卫 → 执行 → 截断结果 | 结构快照定时刷新，数据实时 |
| `api` 接口 | 实时事实：配置、注册信息、状态 | OpenAPI / Swagger 文件或 URL，也可以手工登记 | 导入操作清单 → 勾选允许的操作（默认只开 GET）→ 为操作描述建索引 | 选操作 → Agent 填参数 → 调用 → 按 JSONPath 截取 | 实时 |
| `code` 代码 | 精确符号、调用链 | 绑定的代码仓库 | ripgrep 不需要构建；CodeGraph 走外部服务 | rg / codegraph | 实时 |
| `history` 历史 | 为什么这么写、做过的类似需求 | git log、过往需求的公共存放区 | 不需要构建 / 为存放区建索引 | `git log -S`、存放区检索 | 实时 |

类型通过插件扩展（[13](13-扩展性与生态.md)）。每个类型注册一个 `KnowledgeKind`：

```ts
interface KnowledgeKind {
  kind: string
  title: string; summary: string          // 新建向导里的类型卡片
  intents: KnowledgeIntent[]              // 默认能回答的问题类型
  configSchema: JsonSchema                // 页面表单从这里生成；密钥字段标 format: 'secret'
  test(kb, ctx): Promise<TestResult>      // 测试连接 / 读取第一个文档
  build?(kb, ctx, progress): Promise<BuildResult>   // 不需要构建的类型不实现
  query(kb, q, ctx): Promise<KnowledgeHit[]>
}
```

## 统一模型

```ts
interface KnowledgeBase {
  id: string; name: string; kind: string
  description: string            // 给路由器和人看：能回答什么、不能回答什么
  intents: KnowledgeIntent[]
  scope: 'space' | 'shared'      // shared 放在 spaces 根目录，多个空间可以绑定同一个
  config: Record<string, unknown>          // 按 kind 的 configSchema 校验
  retrieval: { topK: number; minScore?: number; hybrid?: { bm25: number; vector: number }; rerank?: string; budgetTokens: number }
  status: 'draft' | 'building' | 'ready' | 'stale' | 'error'
  version: number                // 发布一次加一；运行时只用已发布的版本
  builtAt?: Timestamp; stats?: { docs: number; chunks: number; bytes: number }
}
```

**存放位置**：

```
<space>/knowledge/<id>/
  kb.json                  # 配置（提交到 git）；密钥只写引用，例如 ${env:PG_URL} 或 secret:<name>
  content/                 # 上传的文档、Wiki 页面（Wiki 在空间内维护时）
  evals/<set>.jsonl        # 评测集（提交到 git）
<space>/.takt/knowledge/<id>/
  v<n>/index/              # 构建产物：倒排表、向量文件、结构快照（不提交，可重建）
  builds/<id>.json         # 构建记录与日志
  evals/runs/<id>.json     # 评测结果
<spaces 根>/.shared/knowledge/<id>/   # 共享知识库，目录结构同上
```

**密钥**存在本机的 `~/.takt/secrets.json`（权限 0600），或者从环境变量读。页面只能写入和替换密钥，不能读出明文。

**向量**：嵌入模型复用模型设置里 openai 兼容的 embeddings 接口。索引是本地文件，结构为 Float32 数组加 JSON 元数据，检索用暴力余弦，十万块以内够用。不引入原生依赖；外部向量库只定插件接口。没配嵌入模型时只用 BM25，页面上会注明。

## 从零建一个知识库（页面）

向导共六步，每一步都可以保存为草稿后退出：

1. **选类型**：每张类型卡片写明"适合回答什么"和一个例子。
2. **接入数据**：
   - rag：拖入文件（md / txt / html / json / csv，其他格式后续再支持），或选仓库路径加 glob，或填 URL 列表；
   - llm-wiki：两种来源。
     - 选已有的 Wiki 目录或仓库；
     - 从代码仓库生成：选仓库、范围 glob 和粒度（按目录或按模块）。
   - database：选驱动，填连接串（存为密钥引用），选 schema 和表白名单；
   - api：填 OpenAPI 地址或上传文件，勾选操作，填认证（密钥引用的请求头）。
3. **测试**：测试连接，并预览前几个文档、表或操作。
4. **构建**：后台任务，通过 SSE 推送进度。
   - 进度分阶段显示：解析 n/N、切块、嵌入、索引；
   - 可以取消，失败时显示日志和出错的文档。
   - "从代码仓库生成 Wiki"作为一次普通运行，跑内置 workflow `kb-wiki-build`：planner 拆模块 → 每个模块一个 agent → 汇总 index → 评审。这样它和需求一样可追溯、可评审。生成结果是一份 Wiki diff 提案，人批准后才合入。
5. **检索测试**：
   - 输入问题，选择 intent 和 topK；
   - 结果显示总分，以及 BM25、向量、rerank 各自的分项；
   - 可以展开原文，也可以对每条结果标"相关"或"不相关"。
   - 标注直接写进评测集。
6. **发布**：
   - 第一次发布是 v1；
   - 之后发布要先过评测门槛（见"召回评测"）；
   - 发布后可以绑定到空间。

也可以让管家代劳：说"帮我从 `docs/` 建一个文档知识库"，管家会生成提案，内容是 `kb.json` 加一次构建。人批准后，构建进度会显示在对话卡片里（[22](22-管家与操作体验.md)）。

## 在项目里怎么用

1. **绑定**：
   - 在空间设置的"知识库"页绑定知识库，空间自己的和共享的都可以绑。
   - 每个绑定可以设置：启用、优先级、覆盖 intents、哪些角色可用。
   - 这一页只管绑定；知识库本身的定义在知识库页面里管理。
2. **节点声明**：

   ```ts
   agent({
     knowledge: {
       bases: ['biz-wiki', 'orders-db'],           // 不写就用空间绑定的全部
       prefetch: [{ text: '退款规则', intent: 'business' }],
       mode: 'both',                              // prefetch | tool | both
     },
   })
   ```

   旧写法 `knowledge: KnowledgeQuery[]` 仍然兼容，等价于 `{ prefetch: [...], mode: 'prefetch' }`。
3. **运行中自取**：
   - native harness 提供 `kb_query` 工具；
   - 外部 harness 用 `takt kb query "<问题>" [--base id] [--intent x]`；
   - 以后接 MCP 工具。
4. **路由**：
   1. intent 推断：先走规则，可选再用模型兜底；
   2. 按 intent 和绑定筛选知识库；
   3. 并行查询，每个库单独设超时；
   4. 用 RRF 合并，再去重；
   5. 按 token 预算截断；
   6. 写入 `context/knowledge/<查询 id>.md`，并记进上下文账本。
5. **留痕**：
   - `knowledge.query` 事件增加以下字段：`queryId`、`bases`、`hits[{ baseId, version, ref, score, rank }]`、`latencyMs`、`tokens`。
   - 节点产物如果引用了某条命中的 `ref`，就发出 `knowledge.used`，作为隐式相关性信号。
6. **回流**：
   - 需求准出后的 `knowledge-writeback` 节点会提出 Wiki diff（见 [08](08-存量项目知识层.md)）。
   - 群聊里人说"这个查错了"，会生成一条评测用例。
   - 归因为"知识缺失、错误或过期"的缺陷，也会生成评测用例（[20](20-评测与归因.md)）。

## 召回评测

**用例**：

```ts
interface KnowledgeEvalCase {
  id: string
  query: string; intent?: KnowledgeIntent
  relevant: Array<{ ref: string; grade: 1 | 2 | 3 }>      // 分级相关性
  answer?: string                                         // 期望事实（数据库 / 接口用期望结果）
  source: 'manual' | 'synthetic' | 'harvested' | 'defect'
  createdAt: Timestamp; createdBy: Actor
}
```

**用例从哪来**：

| 来源 | 怎么产生 | 用途 |
|---|---|---|
| 手工 | 在检索测试里标注 | 发布门槛的主力 |
| 合成 | 模型从文档块出题，每块 1–2 题，人工抽检 | 只做回归。合成题偏向字面重合，不能单独作为发布依据 |
| 线上采集 | 真实查询中被产物引用的命中，成为候选，人确认后入库 | 反映真实分布 |
| 缺陷 | 归因为知识问题的缺陷，生成 `mustFind` 用例 | 防止同一个坑再踩一次 |

**指标**：

- 检索：Recall@5、Recall@10、Precision@k、MRR、nDCG@10、命中率（top k 中至少有 1 条相关）、无结果率、p50/p95 延迟、每次查询的 token。
- 数据库：SQL 执行成功率、结果正确率（和金标准结果集比较）、守卫拦截次数。
- 接口：选对操作的比例、调用成功率。
- 回答忠实度（可选）：答案是否由命中内容支撑。评委模型必须不同于回答模型。

**版本对比与发布门槛**：

- 在同一个评测集上，按用例成对比较两个版本或两组参数。
- 统计方法复用 [21](21-归因可信度加固.md)：Wilson 区间和成对胜负。
- 发布条件：Recall@10 的下降不显著，并且 `defect` 来源的用例全部通过。不满足时，必须填写原因才能强制发布，原因进审计。

**线上监控**（知识库概览页）：

- 无结果率、低分率、引用率的趋势；
- 过期文档数：构建之后源文件又变了的文档；
- 指标恶化时，产生 `knowledge` 风险，交给管家汇报。

**优化闭环**：失败查询列表按诊断分为三类。

| 诊断 | 判定 | 建议 |
|---|---|---|
| 没有相关文档 | 人标注了"应该找到 X"，但 X 不在库里 | 补文档，或把 X 的来源加进数据源 |
| 有文档没召回 | X 在库里，但不在 top k | 加同义词或别名、调小切块、提高 BM25 或向量的权重 |
| 召回了但排名低 | X 在 top k，但排名靠后 | 开启 rerank、调整 `minScore` |

每条建议都可以一键生成"参数变体"，在评测集上跑对比。对比显示更好时，再发布新版本。管家可以把这一串操作打包成提案。

## 安全

- **数据库**：
  - 只允许 `SELECT / WITH / SHOW / DESCRIBE / EXPLAIN`，拒绝多语句；
  - 自动补 `LIMIT`（默认 200）；
  - 设语句超时，并在只读事务中执行（pg 用 `SET TRANSACTION READ ONLY`，mysql 用 `START TRANSACTION READ ONLY`）；
  - 列可以配置脱敏规则：默认对手机号、邮箱、身份证这类模式打码。
- **接口**：只调用勾选过的操作，默认只开 GET；限制响应大小和超时；请求和响应摘要写进事件，认证头不写。
- **构建任务**：在沙箱里读取数据源；URL 抓取遵守空间的网络策略。

## 页面

- **知识库列表** `/s/:space/knowledge`：
  - 每张卡片显示：类型图标、状态、版本、文档数和块数、上次构建时间、7 天查询量、命中率、Recall@10 徽标；
  - 主按钮是"新建知识库"；
  - 空状态展示类型卡片和"让管家帮我建"。
- **知识库详情**共七个 Tab：
  - **概览**：健康状况、使用趋势、绑定关系；
  - **数据源**：增删数据源、手动同步；
  - **构建**：构建历史、进度、日志；
  - **检索测试**；
  - **评测**：评测集、运行、结果、版本对比；
  - **使用**：哪些 workflow、节点、需求查过它，引用率，最近的查询；
  - **设置**：按 schema 生成的表单、检索参数、访问控制、危险操作。
- **空间设置里的"知识库"Tab**：只管绑定，并链到知识库详情。

## 协议变更（摘要）

- **types**：
  - 新增：`KnowledgeBase`、`KnowledgeBinding`、`KnowledgeBuild`、`KnowledgeEvalCase`、`KnowledgeEvalRun`；
  - `AgentNodeDef.knowledge` 支持新写法；
  - `knowledge.query` 事件增加字段；
  - 新增 `knowledge.used`、`knowledge.built`、`knowledge.published` 事件。
- **interfaces**：
  - 新增 `KnowledgeKind`、`KnowledgeStore`；
  - `ProjectStores.knowledge`。
- **api**，所有路由都在 `/api/knowledge` 下：
  - 知识库：`GET/POST /bases`、`GET/PATCH/DELETE /bases/:id`；
  - 测试与构建：`POST /bases/:id/test`、`POST /bases/:id/build`、`GET /bases/:id/builds/:bid`、`GET /bases/:id/builds/:bid/stream`；
  - 检索：`POST /bases/:id/query`（检索测试）；
  - 评测：`GET/POST /bases/:id/evals`、`POST /bases/:id/evals/runs`、`GET /bases/:id/evals/runs/:rid`；
  - 发布：`POST /bases/:id/publish`；
  - 文档：`POST /bases/:id/upload`、`GET /bases/:id/docs`；
  - 类型：`GET /kinds`（返回 `configSchema`）；
  - 绑定：`GET/PUT /api/space/knowledge-bindings`。
- **命令**：
  - 知识库：`knowledge.create`、`knowledge.update`、`knowledge.build`、`knowledge.publish`、`knowledge.bind`；
  - 评测：`knowledge.eval`。

## 不做什么

- PDF、Office 只提取纯文本，版式解析后续再做。
- 外部向量库（Milvus、pgvector 等）只定插件接口，本期不实现。
- 不做文档级 ACL：知识库内的内容对所有被授权角色可见。

## MVP

1. **类型**：
   - rag：本地 BM25，加可选嵌入；
   - llm-wiki：目录或 git，加从代码仓库生成；
   - database：postgres、mysql、sqlite，驱动按需动态加载，加只读守卫；
   - api：OpenAPI 3，只开 GET；
   - code 和 history：把现有实现接入新模型。
2. **页面**：新建向导、构建任务与进度、检索测试与标注、评测集（手工、合成、线上采集）、指标、版本对比、发布门槛。
3. **使用**：空间绑定、节点 `knowledge.bases`、`kb_query` 工具与 CLI、事件扩展。
4. **迁移**：旧 `takt.config.json` 的 `knowledge` 条目自动迁移为 `knowledge/<id>/kb.json`，迁移结果作为提案展示给人确认。
