# 00 · 愿景与要解决的问题

## 一句话

**taktflow 是一条"按节拍走"的 AI 交付流水线**：需求进来，多个 Agent 按代码定义的 DAG 分工完成澄清、设计、编码、测试、修复和准出；每个节点的输入、产物、上下文和判决都落盘、可追溯、可审计、可人工修改后重跑。

"Takt"是精益生产里流水线的节拍：每一站按规范产出，过了门禁才流向下一站。我们要的不是"一个更聪明的编码 Agent"，而是**一条规范、可度量、可审计的交付线**。

## 为什么现在需要它

AI 写代码已经不是瓶颈。大公司已经在强推"全流程走 AI 插件"：PRD、设计稿、spec、门禁文件、测试用例放在一个物料仓库里，AI 澄清需求 → 生成 spec → 拆 task → 按门禁 DAG 执行，人只回答问题和审方案（见参考视频：皮皮虾说《公司正式宣布开始 AI 自动化实现需求》）。但这类系统暴露出几个没解决好的问题：

| 问题 | 现象 | taktflow 的回答 |
|---|---|---|
| **假通过** | AI 自己写、自己测，"跑通"不等于"测对"；流水线 COMPLETED 被当成 PASS | 开发 / 测试 Agent 隔离；门禁 fail-closed；每条用例留证据；判决 Agent 归因（[05](05-判决Agent与修复Loop.md)） |
| **黑盒化** | "代码都不看了，根本看不过来"；没人知道某段代码为什么这么写 | 每个节点的输入、产物、上下文、会话都落盘，追溯链从需求一直到证据（[06](06-追溯与审计.md)） |
| **信息断层** | 人绕过插件直接改，上下文就缺了；Agent 之间靠聊天传话 | 每个需求一个**公共存放区**，所有 Agent 和人都从这里取、往这里写；绕过引擎的改动会被检测出来（[04](04-公共存放区.md)） |
| **长链路成功率低** | 每步 70%，4 步只剩 24%；上下文被压缩后目标丢失 | 每步有产物契约和 validator，带报错重试；状态落文件、断点续跑；上下文账本可视化（[07](07-上下文管理与可视化.md)） |
| **存量项目难接** | 新需求要查历史业务逻辑、接口、表结构、调用链 | 知识层：按问题类型路由到 rg / Wiki / CodeGraph / DB / 接口注册（[08](08-存量项目知识层.md)） |
| **绑死一家模型** | 不同模型在不同环节各有所长；一家 harness 不可用就停摆 | 多 harness × 多模型，按角色和节点选择，可降级（[09](09-多harness与模型路由.md)） |
| **看不到进度** | 管理者只能问人"做到哪了" | 项目总览：阶段条、门禁状态、待办、首跑可用率、人工介入次数、token 成本（[11](11-项目总览与度量.md)） |

## 设计原则

1. **确定的交给代码，不确定的交给模型。** 调度、门禁、证据收集、权限校验是代码；澄清、设计、编码、归因是模型。
2. **文件是唯一事实源。** 状态、产物、事件都在 `.takt/` 里，人能直接读，git 能审阅；不依赖会话记忆。
3. **验证比生成更值钱。** 响亮的失败很便宜，安静的失败最贵；投入优先给 validator 和判决。
4. **生成者和验证者分离。** 写代码的不改测试，写测试的不改代码；验证用不同厂商的模型更好。
5. **人看例外，不看全部。** 人只出现在评审卡点、判决交人和预算用尽的地方。
6. **流程可以长大。** 节点、角色、知识源、harness 都是插件；默认流水线只是一个模板。

## 不做什么

- 不自研一个新的通用编码 Agent。执行内核直接用 Claude Code、Codex、DeepSeek Harness 等现成 harness。
- 不替代项目管理系统（Meego / Jira）。只同步需求和状态，交付过程的细节在 taktflow 里。
- 不承诺"无人值守"。默认保留需求、系分、用例三处人工评审，节拍可以调快，但卡点要显式配置才能去掉。
