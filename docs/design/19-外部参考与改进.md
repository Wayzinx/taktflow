# 19 · 外部参考与改进

## 解决什么问题

M2 之后对照了几个同类项目和一个需求协作平台，发现 taktflow 有几处共性短板：

1. **每个需求都走整条重流程。** 改一行文案也要 PRD → 系分 → 测分 → 交叉评审。同类项目自己的评测数据显示，"治理默认全开"是长任务失败的头号原因：模型把回合花在协调和写流程文件上，而不是干活。
2. **Agent 可以自己宣布完成。** 节点 succeeded 只说明进程正常退出，不说明完成标准达成；常见的假完成是"自检没过，但按格式把文件写出来了"。
3. **同样的失败会空转。** 重试、Loop、判决修复只数次数，不看这次失败和上次是不是同一个、输入有没有变化。
4. **评审状态被压成一个词。** "通过 / 未通过"之外，评审看的是哪个版本、后来产物又改了没有、上轮的问题这轮是不是又出现了，都看不出来；打回后轮次编号还会从 1 重来。
5. **人工确认没绑定版本。** 批准的是 PRD v2，后来改成 v3，批准记录看不出已经过期。
6. **界面重过程、轻决策。** 缺少"已校验 / 已拦截"这类结果度量、预算与异常优先的视图；动效有几处不合规范（进度条动画 width、弹层没有退出动画）。

## 参考了什么

| 来源 | 借鉴 |
|---|---|
| [Metis](https://github.com/Wholiver/metis)（编程 Agent，基于 Pi） | 按"改动形状"分档 T0–T3；每档固定门禁序列；作者不能给自己的评审 / 核验盖章（运行时强制）；失败指纹重复即停；产物环"改 → 验 → 指出具体问题 → 局部改"；自学习只写软层、带试用期与对照组；它自己在 98 个任务上的失败分析（治理默认开、假完成、输出目录污染、隔离 worktree 丢环境） |
| [OpenBitFun](https://github.com/GCWing/OpenBitFun)（Rust Agent 工作台） | 评审 = 记录 + 修订；执行阶段 / 结论 / 覆盖 / 新鲜度互相独立；问题延续（系统观察 vs 人工处置，"本轮没提到"≠"已解决"）；有界评审预算与早停；默认轻量、按风险升级；一个功能只有一个 owner、界面和 Agent 调同一套命令；大任务控制台（异常优先、预算常驻、需要你决策）；提示词按缓存友好顺序拼；动效审计规范 |
| 多 Agent 校验器案例（Grok 多智能体，视频） | 对外交付前必须有独立校验关；"已校验 / 已拦截"是一等指标；控制台的实时计数与事件滚动条 |
| 需求协作平台（调研笔记不入库） | 模板里写**适用场景**，由总负责 Agent 自动选流程；每个节点写**完成标准**；Loop 只在"有东西变了"时才重试；失败分类更细（数据、部署、权限、外部依赖）；人工确认绑定精确版本；措辞调整不触发无关环节重跑；节点按职责派给对应的人；总负责 Agent 一次只问一个最高优先级问题、带推荐选项和影响；节点卡片"目标 + 小结"；产物按 spec 类型分组、可只看当前阶段 |

## 改进清单

### 1. 分档路由与轻量流程

**档位只看改动形状**，不看步数、文件数、模型觉得难不难：

| 档 | 形状 | 默认流程 |
|---|---|---|
| T0 | 改动已经写死（给定 diff / 命令），没有设计 | `quick-fix`：实现 → 校验 |
| T1 | 恰好一个改动面（一个模块 / 目录 / 仓库） | `quick-fix`：短 spec → 实现 → 代码评审 → 交付校验 |
| T2 | 多个改动面，必须串行（共享可变状态、路径重叠、先后依赖） | 标准流水线，研发任务串行 |
| T3 | 多个改动面，路径两两不相交，可并行 | 标准流水线，研发任务并行；不相交检查不过就降为 T2 |

- workflow 新增元数据：`useWhen`（适用场景，自然语言）、`tiers`（适用档位）、`leadInstructions`（总负责准则）、`dynamicRules`（运行中允许 Lead 提议的调整规则）。
- **路由器**（`core/route`）：模型给出 `{ tier, surfaces, workflowId, reason }`，代码做确定性校验——T3 的改动面路径必须两两不相交（glob 交集），否则降为 T2 并写明原因；选中的 workflow 必须声明支持该档；都不满足时用标准流水线。没有模型（mock）时按启发式。
- 结果是一张**路由卡**（`RouteDecision`）：档位、流程、要过的门禁、参与角色、理由。发到需求群，人可以改档（留痕）。`start_run` 的 `workflowId: 'auto'`、`takt route <REQ>`、`takt run --auto` 都走路由器。
- planner 展开时同样检查：条目的写权限有交集就自动加依赖、改为串行。

### 2. 完成标准与结构化自检（防假完成）

- agent 节点新增 `completion: string[]`（完成标准，逐条可验证）。引擎把它拼进 prompt，并要求结果 JSON 带 `checks: [{ id, criterion, pass, evidence }]`。
- **任何一条缺失、`pass: false`、或 `pass: true` 却没有证据，节点就失败**（`完成标准未满足`），不以进程退出码为准。事件 `node.checks`。
- `strictOutputs: true` 时，节点往存放区写了未声明的文件（虚拟环境、缓存、草稿）会被移到隔离区并记 `guard.violation`（rule `output-contract`）。

### 3. 失败指纹：同样的失败不空转

- 指纹 = `节点 : 失败码 : 目标`，再加上**输入身份**（输入产物版本 + worktree HEAD）。
- 同一指纹在输入身份不变的情况下第 2 次出现，就**停止重试**：节点置 blocked，发待办"同样的失败已出现 2 次"，事件 `retry.suppressed`。适用于节点重试、Loop 轮次、判决修复、门禁检查。
- 只有这些情况允许再试：新提交 / 新部署、输入产物有新版本、判决为 `flaky`（仍受 retry 上限约束）。
- 判决类别补充 `test_data`、`deployment`、`permission`、`external_dependency`。

### 4. 评审：记录与修订、正交状态、问题延续

- **记录与修订**：一个 review 节点是一条评审记录；每次打回重做产生一个新**修订**（`revision`），修订内的轮次照常计数，另有全局递增的 `seq`。文件 `reviews/<节点>/r<修订>-round-<轮>.json`。
- **目标指纹**：每轮记录评审时看到的产物版本或代码 HEAD（`targetFingerprint`）。之后产物有新版本 → 该评审**过期**（freshness = stale），但历史结论不改写。
- **状态拆成互相独立的几项**（`ReviewFacets`）：阶段、结论、覆盖（是否所有评审者都给出结论、目标是否都可读）、新鲜度、未关闭问题数。"没发现问题"显示为"无问题 · 当前版本"，不显示成"通过"。
- **问题延续**：问题有 `groupKey`（位置 + 类别 + 标题归一化）和 `fingerprint`（位置、严重度、描述）。每轮由系统算**观察**：新增 / 重复 / 有变化 / 本轮未提及。**处置**（待处理 / 已解决 / 驳回）只能由人显式设置（留痕）；作者回应"已修"但下一轮重复出现，标为"回潮"。
- **预算与早停**：连续 `stopAfterNoProgress`（默认 2）轮没有新增或变化的 blocker / major 问题却仍不通过，提前按 `onExhausted` 处理，不再烧轮次。
- **条件裁决**：配置 `arbiter` 时，只有评审者结论冲突（有人通过、有人要求修改且含 blocker）才请裁决者，不做例行全量评审。
- **作者不能评自己**：`reviewers` 里出现作者角色，`defineWorkflow` 直接报错；rubric 门禁的评审角色与上游产出角色相同时，lint 给警告。

### 5. 人工确认绑定版本；改动分"措辞"和"语义"

- 待办新增 `boundTo`：审批时看到的产物版本。产物之后有新版本，审批显示"已过期"，下游按原有 stale 规则重跑。
- 修改产物时声明影响：`impact: 'cosmetic' | 'semantic'`（默认语义）。**措辞调整只记录，不传播 stale**；Lead 派发的修改任务在 `TaskSpec.impact` 里声明，人可以改判。

### 6. 交付校验与"已校验 / 已拦截"

- 新门禁检查 `acceptance`：每条 AC 都有用例、用例最近一次执行通过、有证据；可选让独立的 `verifier` 角色复核（与产出角色不同）。标准流水线和 quick-fix 都以它结尾。
- AC 标题优先取编号开头的 Markdown 定义行（表格取标题列），找不到才回退首次提及；已撤回的产物不算当前证据。
- 度量新增 `quality`：
  - **已校验**：通过的交付校验与门禁检查数；
  - **已拦截**：交付前被拦下的问题数，按来源拆（门禁、评审、判决的 product_bug、完成标准、失败指纹）。
  - 总览和运行页顶部常驻这两个数。

### 7. 节点负责人与 Lead 行为准则

- 节点新增 `owner`（职责标签，如 `pm` / `rd` / `qa`），空间成员新增 `duties`。待办自动派给职责匹配的人（`assignees`），"派给我"可筛选。
- 节点新增 `goal`（一句话目标），节点结果带 `summary`（一句话小结）。节点卡片只显示这两行，详情折叠。
- Lead 准则（`templates/agents/lead.md` + workflow 的 `leadInstructions`）：
  - 主动推进，能安全默认的不问人（例如没给分支就用默认分支）；
  - 必须问人时一次只问一个最高优先级问题，标"待确认"，给推荐选项和影响；
  - 群里只发关键问题、确认请求、阶段结果和阻塞，过程留在任务里；
  - 结束时先给结论的总览；
  - 任何"通过"都要有证据。

### 8. 统一命令注册表

- 每个"改东西"或"查东西"的功能只有一个 owner：`core/commands` 注册 `CommandSpec`（id、标题、query / command、风险、最低权限、输入 schema）和 handler。
- server 暴露 `GET /api/commands`、`POST /api/commands/:id`；Lead 的动作映射到命令；CLI `takt cmd <id>`；Web 的 ⌘K 列表来自注册表。不再让界面、Lead、CLI 各写一遍同样的校验。
- 首批命令：创建需求、路由预览、启动 / 继续 / 取消运行、回答待办、派发任务、评审问题处置、经验启用 / 退役。

### 9. 预算与异常优先

- `RunBudget { tokens, costUsd, minutes, concurrency }`：来自配置、workflow 默认值或启动参数。
- 并发上限约束同时运行的节点数；用量到 80% 发 `budget.warning` 并由 Lead 通报；到 100% 停止调度新节点，发待办（追加 50% 预算 / 停止）。"只保留核心检查"需要先定义哪些节点算核心，后续再做。
- 需求页顶部：一句话状态 → 执行环境 → 阶段摘要 → **需要你决策** → 预算条。默认不展示完整日志。

### 10. 提示词缓存友好顺序

agent 与 Lead 的 prompt 按"稳定 → 半稳定 → 易变"拼接：角色说明与准则 → 工具 / 技能清单 → 知识与经验 → 备忘 → 状态快照 → 最近消息 → 本次反馈。稳定前缀跨回合逐字节不变，测试覆盖。

### 11. 经验库（自学习，带守卫）

- `knowledge/lessons/<id>.md`：触发条件（角色、路径、错误签名、判决类别）、状态（试用 / 启用 / 退役）、来源、统计（召回、帮助、坑）。
- **学**：运行结束后从判决和评审里零 token 提炼候选（错误签名 + 修复要点），可选用低成本模型整理，受每日预算约束。**守卫**：经验里不能出现绕过门禁、跳过验证一类内容，也不能改 workflow。
- **用**：agent 节点开始时按触发条件召回 ≤3 条、≤600 token；15% 的回合按 `hash(runId + nodeId)` 作为对照组不注入。
- **评**：首次执行成功 → 帮助 +1；失败 → 坑 +1（对照组不记坑）；坑 2 次退役（文件保留）；试用期帮助 5 次转为启用；人明确写下的经验直接启用。

### 12. worktree 环境引导

隔离 worktree 不能丢环境。`RepoBinding` 新增 `bootstrap`（worktree 建好后执行，如 `npm ci`）和 `share`（从镜像软链的大目录，如 `node_modules`）。引导失败时节点直接 blocked 并给出原因，不让 agent 在缺环境的目录里"凑"产物。

### 13. 界面与动效

| 位置 | 改动 |
|---|---|
| 需求群 | 路由卡（档位图标 + 流程 + 门禁 + 角色）；Lead 状态灯（工作：随节拍脉动；等人：琥珀慢闪；空闲：暗呼吸）；"下一步 / 待确认"醒目；从引用跳转时目标行高亮后淡出 |
| 档位图标 | T0 直线、T1 带节点的线、T2 串联、T3 分叉，与节拍标尺母题一致 |
| 总览 / 运行页 | "已校验 / 已拦截"计数、LIVE 标记；运行页底部实时事件滚动条（悬停暂停） |
| 需求列表 | "当前节点"列，状态点区分运行中 / 等人 |
| 需求页 | 预算条与"需要你决策"；产物按 spec 类型分组，可"只看当前阶段" |
| 节点抽屉 | 目标 / 小结两行；完成标准自检清单；失败指纹与被抑制的重试；"告诉 Lead 怎么改" |
| 评审 | 修订时间线；结论 · 覆盖 · 新鲜度三枚标签；问题的观察标记与人工处置；审批过期提示 |
| 空间设置 | 经验 Tab；成员职责；仓库的引导命令与共享目录 |
| workflow 编辑器 | 元数据（适用场景、档位、准则、动态规则）；节点完成标准、负责人、目标 |
| 动效规范 | 进度条用 `scaleX` 不动画 width；弹层 / 对话框 / ⌘K 保留退出动画；直接反馈 80–120ms、弹层与列表 120–180ms、大弹窗进 180–220ms 出 120–180ms；位移 2–8px、缩放不低于 0.985；拖拽本体跟手；流式内容不加入场动画；`npm run motion:audit` 进 CI |

## 不做什么

- 不把档位做成用户必须先选的模式；默认自动路由，人只在路由卡上改。
- 不默认为每个任务生成完整证据包；不因为能并发就并发；不把模型建议升级成阻断。
- 经验库不能改门禁、不能改 workflow；不做语义模糊匹配来关闭评审问题。
- Mini App、多设备中继、皮肤市场不在范围内。

## 落地顺序（M3）

1. **协议**：本文涉及的类型一次加齐（全部可选字段，旧数据兼容）。
2. **并行**：引擎纪律（完成标准、输出契约、失败指纹、预算、交付校验检查、prompt 顺序、经验召回挂点）∥ 评审 v2（修订、正交状态、问题延续、早停、裁决、审批绑定版本、措辞 / 语义）∥ 路由 + 命令注册表 + Lead 准则 ∥ 经验库 + worktree 引导 + 度量 ∥ Web（mock 数据先行）。
3. **接入**：server / CLI / 模板 / 示例 / 演示。
4. **评审与修复**，真实 API 联调，CI。
