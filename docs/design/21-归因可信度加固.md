# 21 · 归因可信度加固

## 解决什么问题

docs/design/20 搭好了评测与归因的骨架：配方、成绩单、缺陷录入与归因、回放评测。但有几处结论**现在还证明不了**，会让"谁的锅、改没改好"变成看起来有依据、实际站不住的判断：

1. **评审当时看到了什么说不清**：引擎记了产物版本，但评审者读的是工作目录里的当前文件，可能已经被改过。
2. **"本该拦住"没有依据**：评审节点只声明了被评审对象，没有比较依据（例如系分评审没带 PRD），也没有职责条目。
3. **身份粒度太粗**：一个评审节点里有多个评审者、作者、可能的 fallback，配方只能说明"用了什么版本"，说明不了"是哪一次调用产出的"。没执行的检查点也无从引用。
4. **请求值被当成实际值**：有的适配器不支持指定模型；技能"声明了"不等于"同步进去了"，更不等于"真的加载了"。
5. **评审结果整轮落盘**：一个评审者失败，其他已完成的结构化结果也丢了。
6. **"已修复"是作者自述**：上一轮的问题这一轮没再提，不代表修好了。
7. **观察和缺陷混在一起**：评审、判决、门禁的自动结论直接当缺陷，会制造误报；按用例自动合并会把不同根因合到一起。
8. **回放没有隔离**：写权限守卫是事后比较，local 沙箱没有文件系统边界，回放可能改到真实空间。
9. **小样本被当成结论**：3 个用例全过，95% 置信区间大约是 44%–100%，说明不了"更好"。
10. **写入一致性没有保证**：缺陷、归因、评测分散在多个文件里，没有统一的追加日志、查重和并发控制。

参考：dsh 插件线上并行做过一版同主题设计，经两轮评审后放弃、以 20 为准；本文吸收了其中被评审确认的做法（分支 `feat/dsh-host-support-v2` 的 `docs/design/19-缺陷归因与改进验证.md`）。

## 设计

### 1. 检查点与"当时看到了什么"（第 1、2、5 点）

- **检查点**：每个评审者（含作者修改、裁决者）、每个 rubric / acceptance 门禁检查项、auditor 与 evaluator 的判断都是一个检查点。
  - `checkpointId = <runId>:<nodeId>:<attempt>:<修订>.<轮>:<评审者或检查项>`；
  - 在**调度时**分配并记 `checkpoint.scheduled`；没执行（出错、被跳过）的检查点也有身份，可以在归因里引用。
- **只读快照**：调用前，把被评审对象和比较依据的**指定版本**物化成只读快照，评审者只读这里，不读工作目录。
  - 快照目录：`.takt/snapshots/<runId>/<checkpointId 安全名>/`；
  - 清单 `SnapshotManifest` 记录每个文件的角色（target / reference）、产物版本、sha256；
  - 只读的实现方式写进清单：沙箱只读挂载、文件权限，或 none。做不到只读时如实记 none，归因只能声称"提供了这些版本"。
- **比较依据与职责**：
  - review 节点新增 `references`（比较依据，glob）；评审者已有的 `checklist` 进入快照清单的职责部分。
  - 评审输出新增 `checklist`：逐条给出 `ok / issue / na`，问题对应到条目。
  - 标准流水线补齐：PRD 评审以澄清结论为依据；系分评审以 PRD 为依据；测分评审以 PRD 和契约为依据。每个评审者都有职责条目，例如"每条验收标准都可验证""契约字段完整"。
- **逐评审者落盘**：每个评审者完成就写 `review.result` 事件和 `reviews/<节点>/r<修订>-round-<轮>/<评审者>.json`，不等本轮其他人。运行恢复时，已完成的评审者不重跑；某个评审者失败，不影响已完成者的结果。

### 2. 调用身份（第 3、4 点）

- **调用（Invocation）** = 一次工作流里的 `HarnessAdapter.run` 尝试（fallback 的每个候选各算一次；harness 内部多轮模型请求只计用量；健康探测不记）。
  - `invocation.started` 记录：节点、attempt、检查点、角色分工（producer / author / reviewer / arbiter / rubric / judge / planner / auditor / evaluator）、fallback 序号、配方键；
  - `invocation.finished` 记录：结果、用量、harness 回报。
  - 产物写入（`artifact.written`、`ArtifactVersion.producedBy`）、评审结果、用量都带上 invocationId。
- **三层取值**：
  - 模型和 effort 分 requested（配方）、resolved（引擎解析）、reported（harness 回报）。适配器不支持覆盖时在 `resolved.applied` 里标 false，不把请求值当实际值。
  - 技能分 declared（角色声明）、provided（实际同步进 harness 技能目录后的内容哈希）、confirmed（harness 事件能证明加载；观测不到记 unknown）。
- **配方不变**：`node.recipe`（docs/design/20）仍是"内容版本"，调用引用它的 recipeKey。

### 3. 问题身份与修复确认（第 6 点）

- **系统管理的问题键**：问题第一次出现时，由引擎分配 `ISS-<n>`（同一运行的同一 review 节点内跨修订有效）。
  - 之后每一轮，prompt 都列出已有问题清单（键、描述、当前状态）；评审者提问题时要么引用已有键，要么声明新问题；模型不能自造键。
  - M3 的 `groupKey` 保留，作为跨运行"可能是同一问题"的合并建议。
- **逐键复查**：评审输出新增 `previous: [{ key, status: resolved / still_open / not_checked, note }]`，对清单里每个未关闭的问题逐条给结论。
  - **只有评审者明确给出 resolved 才算"已验证修复"**；
  - 作者回应 fixed 只记为"声称已修"；
  - 没有复查结论的，保持未关闭。
- facets 的"未关闭问题"和问题延续都改为按问题键计算。

### 4. 观察与缺陷两层（第 7 点）

- **观察（Observation）**：不可变，记录"某个来源在某个时刻对某个对象说了什么"，按源事件幂等入账（幂等键 `<来源>:<runId>:<seq>:<序号>`）。
  - 评审：发现 / 声称已修 / 已验证修复 / 不采纳 / 人工放行。
  - 判决：每个失败对象每次一条；路由为 ignore 的记"忽略"，flaky 的记"不稳定"。
  - 门禁：检查项状态拆成 **pass / fail / error**，error 记为流程问题，不算产物缺陷。
  - 人工、外部缺陷单。
- **缺陷**：
  - 由人从一条或多条观察创建（也可以直接录入外部问题），带有效性（未确认 / 有效 / 不是缺陷 / 重复）与处理状态（待处理 / 声称已修 / 已验证修复 / 接受风险 / 重新打开）。
  - **不按用例自动合并**：同一用例不同轮的失败可能根因不同，一个根因也可能导致多个用例失败。合并只给建议，由人确认，可撤销。
- **漏检判定**（替代 M3 的 `MissReason`，旧字段兼容保留）：

| 结论 | 条件 |
|---|---|
| 本该拦住 | 五项同时满足：① 检查点执行时缺陷已存在（引入点早于它，且快照里的版本包含缺陷内容）；② 相关材料在快照清单里；③ 属于该检查点的职责条目；④ 检查确实执行完成；⑤ 输出里没提出该问题 |
| 拦住了但被放行 | 检查点提出了该问题（同一问题键，或人确认是同一问题），随后被不采纳或人工放行 |
| 没给材料 | 相关材料不在快照清单里 |
| 没执行 | 检查点没执行或执行出错 |
| 不在职责内 | 职责条目明确不包含此类问题 |
| 无法判断 | 以上都证明不了（不用"不在职责内"吸收未知） |

  ②、④ 和"没给材料""没执行"由预检从检查点和快照**确定性**算出；其余由 auditor 给建议，人确认。

### 5. 回放隔离（第 8 点）

- **只回放只读检查点**：评审者、裁决者、rubric、auditor、evaluator 的调用。写代码节点的整节点重执行后续再做，本期明确拒绝。
- **隔离是前置条件**：启动前校验，任一不满足就**拒绝启动**并说明原因。
  - 沙箱为 bwrap / docker，快照只读挂载，网络关闭；
  - 或者 harness 声明了 `readOnly` 能力，并在请求 `readOnly: true` 时不加载写工具和 shell。
  - mock harness 记为"模拟隔离"，只用于测试和演示，报告里显式标注。
- **候选包**：变体指定的技能目录、prompt 文件、角色档案在运行开始时复制成**按内容哈希寻址的不可变候选包**（`.takt/quality/candidates/<id>/`），报告绑定候选包 id。永不写回正式空间。
- **独立环境**：每个样本独立的临时目录与存储，材料来自原检查点的快照，按原清单重映射路径。

### 6. 样本、评委与统计（第 9 点）

- **样本两类**：
  - **必须拦住**（来自确认的漏检）：期望提出某个问题；
  - **无缺陷负样本**（人确认无问题的评审调用）：不应提出 blocker / major，提出就记误报。
- **结论**：每个样本、每个变体重复 N 次（默认 3）。每次结论为 通过 / 失败 / 证据不足；环境错误、无法回放、评委无法判定都是证据不足，**不算通过**。
- **评委**：两组用同一个评委配方；对评委隐藏组别，展示顺序按哈希打乱；评委调用也记调用身份。
- **报告**：
  - 每个样本两组的通过次数；通过率的 Wilson 95% 区间；误报次数；证据不足次数；
  - 样本数或重复次数低于空间配置的发布门槛时，标为**探索性**，不作为发布依据。
- **发布门槛预先规定**：配置 `eval.gate`，包括最少样本数、最少重复次数、允许的通过率下降、允许的误报增加、回归样本必须全过。报告按它给出"达标 / 不达标 / 不适用"，不允许事后改规则后复用旧报告。

### 7. 质量日志与一致性（第 10 点）

- **唯一权威日志**：`.takt/quality/log.jsonl`，复用事件存储的哈希链与链尾锚点。记录：
  - 观察入账；缺陷创建 / 更新；归因记录 / 确认；
  - 评测样本加入 / 退役；评测开始 / 结束；
  - 恢复记录。
- **读模型可重建**：缺陷、归因、样本、评测运行都是从日志重建的读模型，放在 `.takt/quality/views/`，可删可重建。M3 写在存放区的 `defects/<id>.md` 改为给人看的投影；首次加载时把 M3 已有的缺陷、样本**幂等导入**日志。
- **提交**：查重（幂等键）、检查 `baseRevision`、追加、更新锚点，在**同一把提交锁**里完成。人工确认或改判的结论不会被自动结果覆盖。
- **游标**：每个运行已处理到的事件序号存在 `.takt/quality/cursors.json`，提交成功后才推进；崩溃后从游标重放，靠幂等键去重。
- **入口**：
  - `takt run` 结束时同步入账；serve 订阅事件实时入账；
  - `takt quality sync` 补算；
  - `takt quality verify | repair`：链完整、只是锚点没更新时补锚点并记恢复；链被篡改或截断则拒绝，交给人处理。

## 界面

- **节点抽屉"检查点"**：每个检查点的状态、调用身份（requested / resolved / reported）、技能三层；"当时看到的材料"直接打开快照，标出被评审对象和比较依据；职责条目逐条结论。
- **评审**：问题标出系统键 `ISS-n`；"声称已修"与"已验证修复"用不同标记；逐键复查结论。
- **需求页"缺陷与归因"**：上半部分是观察列表（按来源筛选，可多选创建缺陷）；下半部分是缺陷，带有效性 / 处理状态与合并建议；归因卡逐个检查点列出漏检结论，并附五项条件的勾选状态与证据。
- **评测**：隔离校验结果（不满足时显示拒绝原因）；每个样本的重复结果、通过率区间、误报；报告顶部标"探索性"或门槛结论；候选包 id。
- **质量日志状态**：设置页显示日志校验结果，支持一键补算 / 修复锚点（需原因）。

## 不做什么

- 写代码节点的整节点重执行回放、资产的草稿 / 发布状态机：后续再做。
- 语义相似的问题自动合并：只给建议。
- 归因自动确认：始终由人终审。

## 落地顺序（M5）

1. **协议**一次加齐，全部为可选字段，兼容 M3 数据。
2. **第一批并行**：
   - 质量日志与读模型（含 M3 数据导入）；
   - 引擎采集（检查点、快照、调用、三层取值、逐评审者落盘、问题键与逐键复查、门禁三态、标准流水线的依据与职责）；
   - Web（mock 先行）。
3. **第二批并行**：
   - 观察入账与缺陷 / 归因重构（漏检五条件）；
   - 回放隔离、候选包、重复与统计、评委盲评、发布门槛；
   - server / CLI 接入。
4. **评审、修复**，真实 API 联调，CI。
