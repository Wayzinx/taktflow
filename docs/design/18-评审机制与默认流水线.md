# 18 · 评审机制与默认流水线

## 解决什么问题

PRD、系分、测分、代码都要评审，而且应该像真实团队一样**交叉评审**：PM 写的 PRD 由研发和测试评，研发写的系分由产品、测试、架构评，代码由独立的 code review 评。M0 只有"人工批准"和"rubric 打分门禁"，缺了：

- 多个评审者、各自独立上下文；
- 评审结论、问题清单、作者怎么改的，全部留痕；
- 轮次上限：比如三轮还有问题，就打回重新设计，或者交人。

## review 节点

```ts
review({
  id: 'review-prd', title: 'PRD 交叉评审', stage: 'understand', needs: ['prd'],
  target: ['spec/prd.md'],                       // 被评审的产物；代码评审用 { code: { repo: 'app' } }
  author: { role: 'pm' },                        // 按意见修改的角色（独立上下文）
  reviewers: [
    { role: 'rd', focus: '可实现性、接口和数据影响' },
    { role: 'test', focus: '可测性、验收标准是否可验证' },
  ],
  pass: 'all',                                   // all / majority / { minScore }
  maxRounds: 3,                                  // 含首轮
  onExhausted: { rework: 'prd', maxReworks: 1 }, // 或 'human' / 'fail'
  humanSignoff: true,                            // agent 都通过后再交人确认（可选）
})
```

**一轮评审**：
1. 每个评审者开一个**新会话**（可以配不同 harness / 模型，推荐和作者不同厂商），读被评审产物和上下游依据，输出结构化结论：`approve / request_changes / reject`、分数、问题清单（编号、严重程度、位置、描述、建议）。
2. 按 `pass` 规则判断是否通过；通过则（可选人工确认后）结束。
3. 不通过：作者开新会话，拿到全部问题，逐条修改产物并给出**回应**（`fixed / declined / deferred` + 说明），产物生成新版本。
4. 进入下一轮，评审者只看新版本和上轮问题的处理情况。

**轮次用完**：
- `rework`：打回到指定的上游节点（例如重写 PRD 或重新系分），该节点到本评审节点之间的节点重置，上游节点的 prompt 里带上评审意见；打回次数也有上限（`maxReworks`），再超就交人；
- `human`：交人裁决（放行并写理由 / 打回 / 终止）；
- `fail`：运行失败。

**留痕**：每轮写 `reviews/<节点>/round-<n>.json`（全部评审记录 + 作者回应 + 产物版本），汇总 `reviews/<节点>/summary.md`；事件 `review.round`、`review.response`、`review.exhausted`、`rework.started` 进哈希链。Web 上每个评审节点有评审面板：轮次时间线、每个评审者的结论、问题状态（未处理 / 已修 / 不采纳）、版本间差异。

## 默认流水线（作者版）

`templates/workflows/taktflow-standard.workflow.ts`，把这套做法打包成开箱即用的模板，所有参数都能在画布或代码里改：

| 阶段 | 节点 | 评审 |
|---|---|---|
| 需求理解 | 澄清 → 写 PRD（PM） | PRD 交叉评审：RD + Test，≤3 轮，超了打回重写，人确认 |
| 系分设计 | 写系分 + 接口契约（RD） | 系分交叉评审：PM + Test + 架构，≤3 轮，超了打回重新设计，人确认 |
| 测分设计 | 写测分 + 用例（Test，不看代码） | 测分交叉评审：PM + RD，≤3 轮，人确认 |
| 对齐冻结 | 追溯门禁（每条 AC 有用例）→ 冻结基线 | — |
| 研发 | planner 拆任务；每个任务：实现（Dev）→ 代码评审（独立 CR agent，逻辑和写法都看：有更简单的写法、冗余、无意义的防御性判断算 major 要改；≤3 轮，超了打回重做该任务） | 代码评审 |
| 用例转自动化 | 脚本实现（Automation）→ 脚本评审（断言有效性） | 脚本评审 |
| 研发测试 Loop | 执行 → 判决 → 路由修复（修复后过代码评审）→ 再执行 | — |
| 影响面评估 | 影响面分析 | — |
| 准出 | 质量报告 → 交付校验 → 人工准出 → 合入默认分支（冲突时节点失败，手动合好后重试）+ 知识回流 | — |

`templates/workflows/sdlc.workflow.ts` 保留为精简版（没有交叉评审，适合快速试用）。用户可以从任一模板复制，在画布上拖拽或让 AI 改代码，定制自己的流程和角色。
