## 背景

真实运行里一个 run 的 `events.jsonl` 到了 268MB / 39 万行，serve 被拖到 CPU 140%+、内存 4.5GB。上一轮把 `read(afterSeq)` 的尾部补读做成了增量，但还有两条路径每次都整文件处理：

1. **`verify(runId)` 每次整读并重算整条哈希链。** `quality/store.ts` 的 `sync()` 每次先 `verify` 再 `read`；`server/src/maintenance.ts` 给每个运行挂订阅，**每来一批事件就 sync 一次**。所以运行越长，每条新事件的成本越高。
2. **读游标落后于缓存时退回整文件扫描。** 缓存只记一个"读到哪"的游标，任何一次 `read()`（不带 `afterSeq` 的整读、SSE 连接补读、另一个消费者）把游标推到尾部之后，游标稍旧的消费者（例如质量同步）的下一次读就满足不了 `afterSeq >= cached.seq`，又退回整文件。两个消费者交替读同一个运行时，几乎每次都是整文件。

## 任务 1：`verify` 增量化（`fs-events.ts`）

1. 给每个文件缓存"已校验前缀"：`ino`/`size`/`mtimeMs`/`ctimeMs`、校验到的字节位置（最后一个完整行之后）、该位置的最后 `seq` 和 `hash`。
2. 文件只是变长（同 `ino`、`size` 不小于缓存）时，只校验新增部分：从缓存位置往后读，第一条新信封必须满足 `seq = 缓存 seq + 1`、`prevHash = 缓存 hash`，之后逐条按现有规则校验。
3. 文件被替换（`ino` 变）、变短、或同大小但 `mtime`/`ctime` 变了：清缓存，整文件校验（就是现在的逻辑）。
4. 语义与现在完全一致：允许空行、额外信封字段；**末尾没有换行的半行照现在的规则一起校验**，但不进缓存（下次从最后一个完整行之后重新开始）。返回的 `brokenAt` 与整文件校验一致。
5. 校验失败时不缓存失败位置之后的任何东西；下次调用仍能报同样的 `brokenAt`。
6. 能和上一轮的读取缓存、`appendTail` 共用 `fileTails` 就共用；三套状态各自失效条件要写清楚，别互相覆盖出错。
7. 能流式就流式：按块读，不要 `readFile` 整个大文件进内存（整文件校验的退路也尽量按块处理；如果 `verifyChain` 只吃字符串，可以在本文件里写一个按行的等价实现，并用现有测试证明两者等价）。

## 任务 2：落后读者用稀疏检查点定位（`fs-events.ts`）

1. 扫描时每 1000 行记一个检查点 `(seq, 字节位置)`，按文件存；30 万行也只有几百个，内存可以接受。
2. `read(runId, { afterSeq })` 且 `afterSeq < 缓存 seq` 时，二分找 `seq <= afterSeq` 的最后一个检查点，从那里往后读，不再整文件。
3. 文件替换 / 变短时检查点一起清掉。
4. 不带 `afterSeq` 的整读语义不变（仍然要读全部），但顺带建立 / 补齐检查点。

## 任务 3：质量同步别重复做无用功（`quality/store.ts`、`server/src/maintenance.ts`）

1. `sync(runId)` 的 `cursorState()` 每条事件都重读 `cursors.json`，并且每条事件都在锁里写一次 `cursors.json`：改成一批事件处理完后写一次游标（仍保证崩溃安全：先追加观测再推游标，重放靠 key 去重，这条现有保证不能丢）。
2. 不产生观测的事件类型（`harness.message`、`harness.tool` 之类，以 `eventObservations` 返回空为准）也要推进游标，但不要为它们逐条进锁写文件。
3. `maintenance.ts` 给**已结束**的运行也挂了文件订阅（每 300ms stat 一次）：改成只给未结束的运行挂订阅，运行结束后的最后一次 sync 完成再取消。启动时对所有运行各补一次 sync 的行为保留。

## 任务 4：测试

- `verify`：追加后增量校验、半行（无末尾换行）、替换 / 截断回退整文件、中间行被篡改时 `brokenAt` 与整文件一致且重复调用结果稳定、增量段第一条 `prevHash` 不接上时报断链。
- 检查点：两个消费者交替用不同 `afterSeq` 读同一文件，结果与整文件过滤一致。
- 性能（宽松上限，防回退）：5 万行文件上，
  - 每追加 1 条就 `verify` 一次、连续 100 次，总计 < 1s；
  - 两个游标交替（一个追尾、一个落后 500 条）各读 100 次，总计 < 1s。
- 质量同步：一批 1000 条无观测事件只写一次游标文件（spy `writeFileAtomic` 或数文件写次数）；崩溃重放不重复记观测。
- `maintenance`：已结束运行不挂订阅；运行结束后订阅被取消。
